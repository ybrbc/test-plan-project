## 2. Introduction

### 2.1. Назначение документа

Настоящий тест-план определяет общую стратегию, объём, подход и организацию тестирования программной платформы **BookSphere** — масштабируемой e-commerce платформы нового поколения для продажи печатных книг, электронных книг (e-books) и аудиокниг, построенной по архитектуре Headless Commerce.

### 2.2. Область применения (Scope)

План покрывает полное тестирование всех функциональных модулей платформы: клиентской витрины, оформления заказа (Checkout), административной панели (Back-office), мобильных приложений, AI-рекомендаций и интеграций с внешними системами.

### 2.3. Ссылочные документы

- План управления конфигурацией (CM Plan)
- Требования к безопасности: PCI DSS, 152-ФЗ / GDPR
- Архитектурная документация микросервисов
- UX/UI-кит и прототипы (Figma)
- Спецификации API (OpenAPI/Swagger)

## 6. Approach (Общая стратегия тестирования)

### 6.1. Уровни тестирования

| Уровень | Описание | Ответственные |
|---------|----------|---------------|
| **Модульное (Unit)** | Тестирование отдельных микросервисов и функций | Разработчики |
| **Интеграционное** | Взаимодействие микросервисов между собой и с внешними API | QA + Dev |
| **Системное** | Сквозные сценарии (E2E) на стейджинг-среде | QA |
| **Приёмочное (UAT)** | Проверка бизнес-сценариев заказчиком / продакт-менеджером | PO + QA |
| **Нагрузочное** | 10 000 одновременных пользователей, пиковые сценарии | Performance QA |
| **Регрессионное** | После каждого спринта и патча | QA Automation |
| **Безопасность** | Пентест, аудит PCI DSS, 152-ФЗ / GDPR | Security QA / внешний аудитор |

### 6.2. Инструменты

| Параметр | Значения |

### 6.4. Правила регрессионного тестирования

- Полный регрессионный набор выполняется перед каждым релизом.
- Частичный (smoke + критические сценарии) — после каждого мержа в `develop`.
- Регрессия по дефектам: при обнаружении дефекта уровня Critical/Blocker выполняется расширенная регрессия связанного модуля.

### 6.5. Метрики

- Покрытие требований тест-кейсами (целевое ≥ 95%).
- Процент автоматизированных тестов (целевое ≥ 70%).
- Defect Removal Efficiency (DRE).
- Среднее время обнаружения и исправления дефекта.
- Прохождение нагрузочных тестов: время ответа API < 200 мс при 10 000 RPS.

### 6.6. Ограничения и допущения

- Тестирование проводится на стейджинг-среде, идентичной продакшн по конфигурации.
- Внешние sandbox-среды (ЮKassa, СДЭК, 1С) доступны в рабочее время.
- Тестовые данные генерируются скриптами и не содержат реальных ПДн.

## 7. Item Pass/Fail Criteria (Критерии прохождения / непрохождения)

### 7.1. Критерии успешного завершения тестирования

| Критерий | Порог |
|----------|-------|
| Выполнено тест-кейсов | 100% запланированных |
| Пройдено тест-кейсов | ≥ 95% |
| Критические дефекты (Blocker / Critical) | **0** открытых |
| Высокие дефекты (Major) | ≤ 3 открытых (с подтверждённым workaround) |
| Средние / низкие дефекты | Допускаются, фиксируются в backlog |
| Покрытие кода (unit-тесты) | ≥ 80% |
| Нагрузочное тестирование | 10 000 пользователей, API < 200 мс, 0 ошибок при пике |
| Аудит безопасности | Нет уязвимостей уровня High / Critical |
| UAT-подписание | Подписано Продакт-владельцем |

### 7.2. Критерии непрохождения (Fail)

- Обнаружен хотя бы один дефект уровня Blocker, влияющий на Checkout или оплату.
- Время ответа API > 500 мс при нагрузке 5 000 пользователей.
- Утечка персональных данных или обход аутентификации.
- Невозможность синхронизации прогресса чтения между устройствами.

## 8. Suspension Criteria and Resumption Requirements (Критерии приостановки и возобновления)

### 8.1. Приостановка тестирования

Тестирование **приостанавливается**, если:
- Обнаружено ≥ 5 дефектов уровня Blocker в одном модуле.
- Тестовая среда недоступна > 4 часов.
- Критический сбой инфраструктуры (падение K8s-кластера, недоступность БД).
- Изменение требований, затрагивающее > 20% тест-кейсов текущего спринта.

### 8.2. Возобновление тестирования

- После устранения Blocker-дефектов выполняется **расширенная регрессия** затронутого модуля.
- После восстановления среды — повторный **smoke-test** перед продолжением.
- После изменения требований — пересмотр и обновление затронутых тест-кейсов.

| 2 | Внутренняя обработка платежей на стороне банков-эквайеров и платёжных систем (ЮKassa, CloudPayments, Stripe) | Тестируется только корректность вызова API и обработки ответов; внутренняя логика процессинга является ответственностью провайдера и не входит в код BookSphere |
| 3 | Генерация и поставка DRM-защищённых файлов на стороне издательств и агрегаторов (Литрес, Storytel) | Тестируется только приём файлов по API и их корректное сохранение/воспроизведение; процесс создания DRM-файлов — ответственность поставщика контента |

## 6. Approach

### 6.1. Общая стратегия

Тестирование проводится на уровне Master Test Plan и охватывает все уровни: модульное (Unit), интеграционное, системное, приёмочное (Acceptance) и нагрузочное. Стратегия согласована с архитектурой микросервисов и этапами разработки, описанными в паспорте продукта (MVP → Full-версия → QA → Релиз).

Общие правила и процессы:

- **Инструменты автоматизации:** Допущение: для API-тестирования используются фреймворки, совместимые со стеком (например, Pytest для FastAPI, Jest для NestJS, Go testing для Gin); для UI — Playwright/Cypress (Web) и Appium (Mobile). Конкретный набор инструментов определяется в Test Design Specification.
- **Обучение инструментам:** Допущение: при внедрении новых инструментов автоматизации проводится внутреннее обучение команды.
- **Метрики:** собираются метрики покрытия кода, количества дефектов по severity, времени отклика, процента успешных тест-кейсов. Метрики собираются на каждом уровне тестирования.
- **Configuration Management:** управление версиями кода и артефактов через GitLab CI / GitHub Actions; контейнеризация в Kubernetes; версии тестовых сборок фиксируются в реестре артефактов.
- **Конфигурации тестирования:** тестирование проводится в конфигурациях, воспроизводящих целевую среду:
  - Hardware: Допущение: тестовый кластер в Yandex Cloud / AWS, эквивалентный production по топологии.
  - Software: все микросервисы в контейнерах, идентичные production-образам.
  - Комбинации: Web (Chrome, Firefox, Safari), Mobile (iOS, Android), Smart TV, голосовые ассистенты.
- **Регрессионное тестирование:** регрессионный набор запускается при каждом новом билде микросервиса. Объём регрессии определяется по severity обнаруженных дефектов: при критических дефектах — полный регресс; при незначительных — целевой регресс затронутых модулей.
- **Обработка нетестируемых требований:** элементы требований, признанные нетестируемыми или некорректными, фиксируются в Test Incident Report и эскалируются на уровень Product Owner.
- **Методологии:** Допущение: применяются техники тест-дизайна на основе эквивалентных классов, граничных значений, парного тестирования (pairwise) для комбинаций форматов и способов оплаты.
- **Ограничения:** Допущение: ограничения по ресурсам и срокам определяются Project Plan.

### 6.2. Подход к тестированию DRM-сервера

- **Функциональное тестирование:** проверка шифрования файлов, корректности выдачи лицензий, ограничений на копирование/перенос.
- **Негативное тестирование:** попытки обхода DRM (модификация запросов, повторное использование токенов, доступ без авторизации).
- **Интеграционное тестирование:** взаимодействие DRM-сервера с Object Storage (S3), микросервисом каталога, мобильным приложением (оффлайн-режим).
- **Тестирование производительности:** время выдачи лицензии и расшифровки фрагмента при нагрузке 10 000 одновременных пользователей.
- **Соответствие требованиям:** проверка, что защита e-books соответствует условиям договоров с поставщиками контента (Литрес, Storytel).

### 6.3. Подход к тестированию AI-рекомендаций

- **Функциональное тестирование:** проверка формирования персональной ленты «Для вас» на основе прочитанного, оценок и поведения (коллаборативная фильтрация).
- **Тестирование данных:** верификация корректности входных данных (история покупок, оценки, поведенческие события из MongoDB и PostgreSQL).
- **Интеграционное тестирование:** взаимодействие микросервиса на Python (PyTorch / TensorFlow) с API Gateway и витриной.
- **Нагрузочное тестирование:** генерация рекомендаций при 10 000 одновременных пользователей; время ответа микросервиса < 200 мс.
- **Тестирование качества моделей:** Допущение: метрики качества рекомендаций (precision, recall, coverage) определяются в Test Design Specification и согласуются с продуктовой командой.
- **Регрессионное тестирование:** при обновлении моделей проверяется отсутствие деградации качества на контрольном датасете.

### 6.4. Подход к тестированию платёжных интеграций

- **Интеграционное тестирование:** проверка взаимодействия с ЮKassa, CloudPayments, Stripe в sandbox-режиме для всех способов оплаты (карты, СБП, крипто-кошельки, рассрочка/сплит).
- **Функциональное тестирование:** успешная оплата, отклонение оплаты, частичный возврат, полный возврат, повторная попытка.
- **Негативное тестирование:** невалидные данные карты, истёкший срок, недостаточный баланс, таймаут платёжного шлюза.
- **Безопасность:** верификация соответствия PCI DSS — данные карт не логируются, не хранятся в открытом виде, передаются по TLS.
- **Нагрузочное тестирование:** обработка транзакций при 10 000 одновременных пользователей.
- **Регрессионное тестирование:** при каждом обновлении платёжного модуля — полный набор интеграционных тестов по всем провайдерам.

### 6.5. Специальные требования

- Тестирование проводится только на полном компоненте (микросервисе) после его сборки и деплоя в тестовое окружение.
- Взаимосвязанные функции (например, оформление заказа → расчёт доставки → оплата → списание бонусов) тестируются совместно как сквозной сценарий (End-to-End).
- Допущение: для AR-витрины требуется физическое устройство с камерой; тестирование проводится на ограниченном наборе устройств.

## 7. Item Pass/Fail Criteria

### 7.1. Критерии для уровня Unit / Integration Test

| Критерий | Измерение |
|---|---|
| Все запланированные тест-кейсы выполнены | 100 % тест-кейсов уровня выполнены |
| Процент успешных тест-кейсов | ≥ 95 % пройдено без дефектов; ≤ 5 % с дефектами severity Low/Trivial |
| Покрытие кода (для микросервисов) | ≥ 80 % по данным инструмента code coverage |
| Критические дефекты (severity Critical, Blocker) | 0 открытых дефектов |

### 7.2. Критерии для уровня System / End-to-End Test

| Критерий | Измерение |
|---|---|
| Все функциональные сценарии (из раздела 4) пройдены | 100 % сценариев выполнено |
| Дефекты severity Critical / Blocker | 0 открытых |
| Дефекты severity High | ≤ 3 открытых, каждый с утверждённым workaround |
| Дефекты severity Medium / Low | Допустимы при наличии плана исправления до релиза |

### 7.3. Критерии нагрузочного тестирования

| Критерий | Измерение |
|---|---|
| Одновременная нагрузка | 10 000 одновременных пользователей |
| Среднее время ответа API | < 200 мс (при нагрузке 10 000 одновременных пользователей) |
| Процент успешных запросов при пиковой нагрузке | ≥ 99,9 % |
| Ошибки 5xx при нагрузке | ≤ 0,1 % от общего числа запросов |
| Доступность (SLA) | 99,9 % (не более 8 часов простоя в год, включая плановые работы) |
| Auto-scaling | Микросервисы масштабируются горизонтально при достижении порога нагрузки; время масштабирования ≤ 60 секунд |

### 7.4. Критерии для уровня Master Test Plan (приёмка)

| Критерий | Измерение |
|---|---|
| Все тест-планы нижнего уровня завершены | 100 % дочерних планов закрыты со статусом Pass |
| Все тест-планы без ошибок | ≥ 90 % планов закрыты без открытых дефектов |
| Планы с незначительными дефектами | ≤ 10 % планов с открытыми дефектами только severity Low |
| Аудит безопасности | 0 уязвимостей уровня Critical/High по результатам аудита (PCI DSS, 152-ФЗ, GDPR, защита от DDoS, SQL-инъекций) |

## 8. Suspension Criteria and Resumption Requirements

### 8.1. Критерии приостановки тестирования

| Условие | Действие |
|---|---|
| Обнаружено ≥ 5 дефектов severity Critical/Blocker в одном микросервисе | Тестирование данного микросервиса приостанавливается; команда разработки устраняет дефекты |
| Обнаружен дефект, блокирующий > 50 % оставшихся тест-кейсов | Тестирование приостанавливается до устранения блокирующего дефекта |
| Тестовое окружение (Kubernetes, БД, внешние sandbox) недоступно > 4 часов | Тестирование приостанавливается до восстановления окружения |
| Время ответа API стабильно превышает 200 мс при нагрузке ниже 10 000 одновременных пользователей | Нагрузочное тестирование приостанавливается для анализа причин |

### 8.2. Требования к возобновлению

- После устранения блокирующих дефектов выполняется **полный регрессионный прогон** по затронутым модулям.
- После восстановления тестового окружения выполняется **смоук-тест** (Smoke Test) перед продолжением основного тестирования.
- Допущение: решение о возобновлении принимает Lead QA Engineer совместно с Development Lead.
- Дефекты, обнаруженные после возобновления, классифицируются отдельно; «призрачные» ошибки, вызванные предшествующими неисправленными дефектами, не учитываются в статистике.

## 6. Approach

### 6.1 Overall Strategy

Тестирование выполняется по уровням: unit → integration → system → load → security, с применением риск-ориентированного подхода. Стратегия согласована на всех уровнях (от модульных до приёмочных испытаний). Тестирование проводится на выделенном стенде в Yandex Cloud (A2, A5). CI/CD на GitLab CI обеспечивает автоматический запуск unit- и интеграционных тестов при каждом merge request (A7).

### 6.2 Tools

|---|---|---|
| Управление тест-кейсами и дефектами | Jira + Zephyr Scale | Единый трекер задач и тестов; интеграция с GitLab CI |
| Unit-тестирование: Python (FastAPI) | pytest + coverage.py | Стандарт для Python-проектов; покрытие ≥ 80% (рекомендуемый) |

### 6.4 Specialized Testing Approaches

**DRM-сервер:**
Тестирование проводится на эмуляторе DRM до интеграции с Литрес/Storytel (A8), затем — на реальном сервере. Проверяются: шифрование файлов, выдача и отзыв лицензий, корректная работа офлайн-лицензий на мобильных устройствах, защита от копирования во фрагменте «Look Inside», деградация при недоступности DRM-сервера.

**AI-рекомендации:**
Верификация качества модели выполняется на синтетическом датасете (A4): метрики precision@10, recall@10, NDCG@10. Порог: NDCG@10 ≥ 0,35 (рекомендуемый, обоснование: типичный порог для коллаборативной фильтрации в e-commerce). Тестирование деградации: при недоступности сервиса рекомендаций витрина отображает статический список бестселлеров. Нагрузочный тест: сервис рекомендаций не должен превышать время ответа 500 мс при 10 000 одновременных запросов (рекомендуемый; 500 мс — верхняя граница допустимого UX-порога для фоновой загрузки).

**Платёжные интеграции (ЮKassa, CloudPayments, Stripe):**
Тестирование только в sandbox-окружениях (A3). Покрываются: успешная оплата, отказ, частичный возврат, полный возврат, двойной callback (идемпотентность), таймаут платёжного шлюза, переключение на альтернативный шлюз при недоступности основного. Тестовые суммы ограничены минимальными значениями.

**Поиск на Elasticsearch:**
Тестирование релевантности на подготовленном датасете из 50 000 синтетических книг (A4). Проверяются: опечатки (расстояние Левенштейна ≤ 2), синонимы, морфология (падежи, множественное число), фильтрация по всем атрибутам (жанр, автор, издательство, год, рейтинг, цена, формат). Время ответа поиска ≤ 200 мс при 10 000 одновременных запросов.

**Согласованность данных между микросервисами:**
Применяется подход контрактного тестирования (contract testing) через Postman/Newman: каждый микросервис публикует контракт (схема запроса/ответа), и контрагенты проверяются на совместимость. Дополнительно проверяется: консистентность остатков между 1С/МойСклад и каталогом, статусы заказа между NestJS и службами доставки, баланс бонусов между Заказами и Пользователями.

**Offline-режим Flutter:**
Тестирование на реальных устройствах (минимум 3 модели: iPhone 14, Samsung Galaxy S23, бюджетный Android). Сценарии: скачивание e-book → отключение сети → чтение → восстановление сети → синхронизация прогресса. Проверка целостности данных при обрыве загрузки, при переполнении хранилища, при обновлении приложения в офлайн.

### 6.5 Regression Testing

Регрессионное тестирование запускается при каждом merge request (unit + интеграционные автотесты в CI/CD). Полная регрессия (все уровни) — при каждом релиз-кандидате. Объём регрессии определяется по матрице влияния: изменение в микросервисе → регрессия всех функций, зависящих от него (см. раздел 3, столбец «Зависимости»).

### 6.6 Configuration Management

Все тест-кейсы, скрипты, отчёты хранятся в GitLab-репозитории проекта. Версионирование привязано к версии сборки в GitLab CI. Конфигурация стенда управляется через Helm + Terraform и фиксируется в репозитории.

### 6.7 Constraints

- Сроки тестирования зависят от сроков разработки (раздел Schedule).
- Нагрузочный стенд доступен только в период этапа «QA и Нагрузочное тестирование» (1 месяц) для контроля стоимости облачных ресурсов (рекомендуемый).
- Тестирование PCI DSS-аспектов не заменяет внешний QSA-аудит (A9).

## 8. Suspension Criteria and Resumption Requirements

### 8.1 Suspension Criteria

Тестирование приостанавливается, если выполняется любое из условий:

| Условие | Обоснование |
|---|---|
| Обнаружено ≥ 5 дефектов приоритета Critical / Blocker в одном функциональном модуле, не исправленных в течение 2 рабочих дней | Продолжение генерирует каскадные ложные дефекты |
| Недоступность ключевого стенда или внешнего sandbox-сервиса > 4 часов подряд (рекомендуемый) | Невозможность выполнения тестов |
| Defect density в отдельном микросервисе превышает 10 дефектов на 1000 строк кода (рекомендуемый) | Код нестабилен; тестирование неэффективно |
| Критический сбой инфраструктуры стенда (падение K8s-кластера, недоступность БД) > 2 часов | Тестовые результаты невалидны |

### 8.2 Resumption Requirements

- Все дефекты, вызвавшие приостановку, исправлены и подтверждены повторным тестом.
- Проводится регрессионный прогон по всем тест-кейсам приостановленного модуля.
- Если приостановка длилась > 5 рабочих дней, выполняется повторный smoke-тест стенда перед возобновлением.
- Решение о возобновлении принимает QA Lead (раздел 12).

### 14.3 Правила при сдвиге сроков

1. Все тестовые даты привязаны к датам поставки сборок разработкой, а не к календарным датам. Если передача сборки задерживается на N дней, начало тестирования сдвигается на N дней от фактической даты передачи.
2. Если сдвиг разработки превышает 10 рабочих дней (рекомендуемый), проводится пересмотр объёма тестирования: в первую очередь сокращаются функции с риском L, затем M. Функции с риском H не сокращаются.
3. Решение о сокращении объёма принимается совместно QA Lead и Product Owner и фиксируется в Jira.
4. Сокращение тестирования из-за сдвига сроков разработки не должно приводить к снижению критериев раздела 7 для функций с риском H.
5. Информация о сдвиге и его последствиях доводится до всех заинтересованных сторон в течение 1 рабочего дня.

## 6. Approach

### 6.1. Общая стратегия

Тестирование проводится на четырёх уровнях: модульное (unit), интеграционное (integration), системное (system), нагрузочное и безопасности (load & security). Модульное и интеграционное тестирование выполняются параллельно с разработкой в CI/CD (GitLab CI). Системное и нагрузочное тестирование концентрируются на этапе «QA и Нагрузочное тестирование» и частично на этапе разработки Full-версии.

### 6.2. Таблица инструментов

| Назначение | Инструмент | Обоснование |
|---|---|---|
| Модульное тестирование: FastAPI (Каталог, AI) | pytest, httpx | Стандарт для Python; httpx для async-тестов API |
| Модульное тестирование: NestJS (Корзина, Заказы) | Jest, supertest | Встроен в NestJS; supertest для HTTP-тестов |
| Модульное тестирование: Go, Gin (Пользователи) | go test -cover | Стандартный инструмент Go; флаг -cover для метрики покрытия |
| Модульное тестирование: Flutter (Mobile) | flutter_test, integration_test | Встроенные средства Flutter для widget- и integration-тестов |
| Контрактное тестирование микросервисов | Pact | Верификация контрактов между сервисами без развёртывания всей системы |
| API-автоматизация (системный уровень) | Postman / Newman | Коллекции запросов, запуск в CI |
| E2E Web-тестирование | Playwright | Поддержка SSR/SSG Next.js; параллельный запуск браузеров |

| Тестирование безопасности | OWASP ZAP, Burp Suite Professional | Автоматическое сканирование уязвимостей + ручная проверка (A7) |
| Тестирование поиска Elasticsearch | pytest + elasticsearch-py | Скрипты проверки релевантности, морфологии, опечаток |
| Мониторинг и алёрты при нагрузке | Prometheus, Grafana, Sentry | Входят в стек продукта; используются для наблюдения в реальном времени |
| Управление тест-кейсами и дефектами | TestRail, Jira | Централизованный учёт; интеграция с GitLab CI |
| Управление тестовыми данными | Собственные скрипты генерации (Python) | Синтетические данные по A3, A10 |

### 6.4. Специализированные подходы

**Тестирование DRM-сервера.** Проверяются: шифрование и расшифровка файлов, валидность и истечение лицензий, привязка к устройству/аккаунту, защита от копирования в Look Inside. Используются тестовые файлы с валидными и истёкшими лицензиями, предоставленные разработкой (A4). Файлы и лицензии поставщиков (Литрес, Storytel) эмулируются для проверки корректного приёма и хранения (A2). DRM-сервер тестируется как компонент платформы; эмулятор не заменяет его, а подменяет только внешние файлы.

**Тестирование AI-рекомендаций.** Проверяются: корректность ответов при холодном старте (новый пользователь), персонализация на основе оценок и истории, деградация при отсутствии данных. Нагрузочная проверка: время инференса модели укладывается в < 200 мс наравне с остальными сервисами. Качество оценивается на размеченном датасете по hit-rate@10 (A5).

**Тестирование платёжных интеграций.** Каждый провайдер (ЮKassa, CloudPayments, Stripe) тестируется в sandbox (A2). Проверяются: успешный платёж, отказ, таймаут, повторный callback (идемпотентность), возврат (refund), переключение провайдера при недоступности основного. Тесты автоматизированы в Newman и запускаются в CI.

**Тестирование поиска на Elasticsearch.** Проверяются: релевантность по точному запросу, толерантность к опечаткам, морфологический поиск, синонимы, комбинированные фильтры (жанр, автор, издательство, год, формат, цена, рейтинг). Производится нагрузочная проверка поиска при 10 000 одновременных пользователей. Тестовый каталог: 50 000 SKU (A3), расширенный до 100 000 для нагрузки.

**Согласованность данных между микросервисами.** Применяется контрактное тестирование (Pact) для каждой пары взаимодействующих сервисов. Проверяются: сага-паттерны при создании заказа (резервирование на складе → списание → оплата → уведомление), компенсационные транзакции при отказе одного из участников, идемпотентность событий. Тесты на eventual consistency: запись в один сервис и чтение из другого с допустимой задержкой ≤ 2 с (рекомендуемый).

**Тестирование offline-режима Flutter.** Проверяются: загрузка e-book для офлайн-чтения, работа аудиоплеера без сети, синхронизация прогресса при восстановлении соединения, разрешение конфликтов (чтение на двух устройствах офлайн). Покрытие: 5 моделей на iOS 16+ и 5 на Android 12+ (A8). Используются интеграционные тесты из пакета integration_test и ручное тестирование.

### 6.5. Конфигурации тестирования

Тестируются две конфигурации окружения (A1):
- **Staging-full:** полный набор микросервисов, баз данных и интеграций в Kubernetes.
- **Staging-perf:** изолированный кластер для нагрузочных тестов, идентичный staging-full по ресурсам.

### 6.6. Регрессионные правила

Регрессия запускается: при каждом мерже в основную ветку (автоматически в GitLab CI), перед каждым релизным кандидатом, после исправления дефекта с severity ≥ High. Объём регрессии: 100 % автоматизированного набора при релизе; целевой набор (затронутые модули + интеграции) при мерже.

## 7. Item Pass/Fail Criteria

### Unit-уровень

- Покрытие кода ≥ 80 % для каждого микросервиса (по данным go test -cover, pytest --cov, Jest --coverage, flutter_test --coverage) (рекомендуемый).
- Все модульные тесты пройдены; 0 тестов со статусом Failed.

### Integration-уровень

- Все контракты между парами микросервисов подтверждены (Pact-верификация: 0 ошибок).
- Интеграционные сценарии (создание заказа, оплата, доставка, подписка) пройдены на 100 %.
- Допустимо: ≤ 3 дефекта с severity Low, не влияющих на основной поток.

### System-уровень

- Все тест-кейсы выполнены; ≥ 95 % пройдено (рекомендуемый).
- Дефекты с severity Critical и Blocker: 0.
- Дефекты с severity High: ≤ 5 при наличии подтверждённого workaround (рекомендуемый).
- Дефекты с severity Medium и Low: фиксируются, но не блокируют релиз при наличии плана исправления.

### Load-уровень

- Время ответа всех микросервисов (включая AI-рекомендации): < 200 мс при 10 000 одновременных пользователей.
- p99: ≤ 350 мс (рекомендуемый).
- Ошибок 5xx: < 0,1 % от общего числа запросов за прогон (рекомендуемый).
- Ступенчатая нагрузка: 1 000 → 5 000 → 10 000 VU, выдержка на каждой ступени не менее 10 мин.
- Auto-scaling: время масштабирования пода ≤ 90 с при переходе со ступени 5 000 на 10 000 VU (рекомендуемый).
- Выносливость (endurance): 4 ч при 7 000 VU без утечек памяти (рост потребления RAM ≤ 5 %) (рекомендуемый).

### Security-уровень

- 0 уязвимостей с severity Critical и High по результатам сканирования OWASP ZAP и ручной проверки (A7).
- PCI DSS SAQ-D: все применимые требования выполнены.
- 152-ФЗ / GDPR: персональные данные шифруются при хранении и передаче; запрос на удаление данных выполняется ≤ 30 дней.
- SQL-инъекции и XSS: 0 подтверждённых уязвимостей.
- DDoS-устойчивость: сервис выдерживает тестовую нагрузку, превышающую штатную в 3 раза, без деградации (рекомендуемый).

### Доступность (SLA)

SLA 99,9 % проверяется не разовым нагрузочным прогоном, а непрерывным мониторингом (Prometheus, Grafana) и серией failover-тестов: остановка пода микросервиса, отказ узла базы данных, деградация сети. Суммарный допустимый простой на плановые работы — не более 8 часов в год. Критерий прохождения: за время наблюдения на стенде не зафиксировано незапланированного простоя; переключение при сбое занимает ≤ 30 с (рекомендуемый).

## 8. Suspension Criteria and Resumption Requirements

### Критерии приостановки

- Обнаружено ≥ 3 дефектов с severity Critical в одном компоненте за одну сессию тестирования — тестирование данного компонента приостанавливается до исправления.
- Частота ошибок 5xx при нагрузочном тестировании превышает 5 % на любой ступени — прогон останавливается, проводится анализ.
- Доступность стенда ниже 90 % в течение рабочей сессии — тестирование приостанавливается до восстановления инфраструктуры.

### Возобновление

- После исправления дефектов, вызвавших приостановку, выполняется регрессионный прогон затронутых модулей.
- Нагрузочное тестирование после критического сбоя возобновляется со ступени, предшествующей ступени сбоя.
- Решение о возобновлении принимает QA Lead; при разногласиях — эскалация на Project Manager.

## 11. Environmental Needs

### Стенды

| Стенд | Назначение | Конфигурация |
|---|---|---|
| Staging-full | Функциональное, интеграционное, системное тестирование | Кластер Kubernetes: 3 master-узла + 6 worker-узлов (3 для сервисов, 3 для БД); все микросервисы, БД, интеграции (A1) |
| Staging-perf | Нагрузочное и выносливостное тестирование | Идентичен Staging-full по ресурсам; изолирован для исключения взаимного влияния |
| Mobile-lab | Тестирование Flutter-приложения | 5 устройств iOS 16+ и 5 устройств Android 12+ (A8); стенд с ограничением сети для проверки offline |

### Тестовые данные

Синтетические данные генерируются скриптами на Python (A3, A10):
- Каталог: 50 000 SKU (100 000 для нагрузки).
- Пользователи: 10 000 профилей с различными ролями.
- Заказы: 5 000 в различных статусах.
- Медиафайлы: обложки, фрагменты, аудиофрагменты в S3.
- DRM-файлы: тестовые зашифрованные файлы с валидными и истёкшими лицензиями (A4).

### Сетевые требования

- Доступ к sandbox-окружениям внешних сервисов (ЮKassa, СДЭК, 1С, Bitrix24, Литрес, Storytel, SendGrid, Twilio) (A2).
- Изоляция стендов от продуктовой сети.
- Доступ к GitLab CI для запуска автоматизированных тестов.

### Ограничения

- На нагрузочном стенде не выполняются функциональные тесты.
- Во время нагрузочного тестирования внешние интеграции работают через эмуляторы для исключения лимитов провайдеров.
