## 1. Введение (Introduction)

### 1.1 Цель (Purpose)
Настоящий Тест-план для проекта BookSphere определяет стратегию, ресурсы, график и артефакты тестирования. Основные цели:
* Определить компоненты и микросервисы платформы, подлежащие тестированию.
* Зафиксировать высокоуровневые требования к тестированию (функциональные и нефункциональные).
* Описать стратегии тестирования для Headless Commerce архитектуры, микросервисов, мобильных и веб-клиентов.
* Оценить необходимые ресурсы и инфраструктуру для обеспечения SLA 99.9% и поддержки 10 000 одновременных пользователей.

### 1.2 Предпосылки (Background)
**BookSphere** — это масштабируемая e-commerce платформа нового поколения (архитектура Headless Commerce) для продажи печатных книг, e-books и аудиокниг. 
* **Целевая аудитория:** B2C, B2B (библиотеки, корпоративные клиенты), внутренние пользователи.
* **Архитектура:** Микросервисная (Python/FastAPI, Node.js/NestJS, Go/Gin), контейнеризация (Kubernetes), Headless CMS (Strapi).
* **Клиенты:** Web (Next.js), Mobile (Flutter с оффлайн-режимом и DRM), AR-витрина.
* **БД и Хранилища:** PostgreSQL, Redis, MongoDB, S3.
* **Интеграции:** 1С, платежные шлюзы (ЮKassa, Stripe), логистика (СДЭК, Shiptor), поставщики контента (Литрес).

### 1.3 Область применения (Scope)
**Что тестируется (In-Scope):**
* API Gateway и все микросервисы (Каталог, Корзина, Пользователи, AI-рекомендации).
* Клиентские приложения: Web (Next.js), Mobile (iOS/Android на Flutter).
* Административная панель (Back-office / PIM / OMS).
* Нефункциональные требования: Нагрузочное тестирование (10k пользователей, API < 200 мс), Безопасность (PCI DSS, 152-ФЗ, DRM), Отказоустойчивость (K8s, БД).
* Внешние интеграции (точка входа/выхода API, мокирование ответов 3-х сторонних систем).

**Что НЕ тестируется (Out-of-Scope):**
* Внутренняя бизнес-логика сторонних систем (1С, банки, службы доставки) — тестируются только контракты API и сценарии обработки ошибок/таймаутов.

## 3. Стратегия тестирования (Test Strategy)

### 3.1 Типы тестирования (Testing Types)

#### 3.1.1 Тестирование целостности данных и БД (Data and Database Integrity)
* **Цель:** Обеспечить консистентность данных между реляционными (PostgreSQL), документными (MongoDB) и кэширующими (Redis) хранилищами.
* **Техника:** Проверка транзакций в PostgreSQL (заказы, финансы), синхронизация корзин в Redis, целостность метаданных отзывов в MongoDB. Проверка DRM-ключей и ссылок на S3.
* **Критерий завершения:** Отсутствие рассинхронизации данных между микросервисами при сбоях и высоких нагрузках.

#### 3.1.2 Функциональное тестирование (Function Testing)
* **Цель:** Проверка бизнес-логики микросервисов и API (FastAPI, NestJS, Go).
* **Техника:** Black-box тестирование API (Postman/RestAssured). Проверка сценариев: добавление в корзину, применение промокодов, расчет доставки (интеграция с API СДЭК/Boxberry), обработка вебхуков от платежных шлюзов.
* **Особенность:** Тестирование AI-рекомендаций (корректность выдачи на основе коллаборативной фильтрации).

#### 3.1.3 Тестирование бизнес-циклов (Business Cycle Testing)
* **Цель:** Эмуляция сквозных бизнес-процессов во времени.
* **Техника:** 
  * *Цикл подписки:* Продление, списание средств, истечение срока, доступ к DRM-контенту.
  * *B2B цикл:* Массовая закупка корпоративной библиотеки, генерация закрывающих документов, интеграция с ERP.
  * *Маркетплейс:* Публикация товара сторонним продавцом, заказ, комиссия, выплата.

#### 3.1.4 Тестирование пользовательского интерфейса (User Interface Testing)
* **Цель:** Проверка UX/UI на Web (Next.js), Mobile (Flutter) и в AR-среде.
* **Техника:** Кроссбраузерное и кроссплатформенное тестирование. Проверка микроанимаций (Framer Motion), адаптивности, навигации. Тестирование AR-витрины (распознавание физических книг камерой).
* **Особенность:** Тестирование гибридного ридера (Immersion Reading - синхронизация текста и аудио).

#### 3.1.5 - 3.1.8 Профилирование, Нагрузочное, Стресс- и Объемное тестирование
* **Цель:** Подтверждение NFR (API < 200 мс, 10 000 юзеров, Auto-scaling).
* **Техника:** 
  * *Нагрузочное (K6/JMeter):* Эмуляция пиковой нагрузки во время распродаж (10k concurrent users). Тестирование поиска (Elasticsearch) на объемных данных (миллионы книг).
  * *Стресс-тестирование:* Ограничение ресурсов подов в Kubernetes, тестирование механизмов Auto-scaling.
  * *Объемное:* Заполнение S3 и MongoDB тестовыми медиафайлами и отзывами до достижения лимитов, проверка деградации производительности.
* **Критерий завершения:** Система масштабируется автоматически, время ответа API не превышает 200 мс при 95-м перцентиле нагрузки, нет утечек памяти.

#### 3.1.9 Тестирование безопасности и контроля доступа (Security and Access Control)
* **Цель:** Защита данных, соответствие PCI DSS и 152-ФЗ, защита DRM.
* **Техника:** 
  * *Сканеры уязвимостей (DAST/SAST):* Поиск SQLi, XSS, DDoS-устойчивость.
  * *RBAC (Role-Based Access Control):* Разграничение прав B2C, B2B, Контент-менеджеров, Операторов.
  * *DRM-тестирование:* Попытки обхода шифрования e-books, извлечения аудиофайлов, копирования фрагментов (Look Inside).
  * *Пентест:* Аудит платежного шлюза и передачи персональных данных.

#### 3.1.10 Тестирование отказоустойчивости и восстановления (Failover and Recovery)
* **Цель:** Проверка SLA 99.9% и устойчивости микросервисной архитектуры.
* **Техника:** Chaos Engineering (например, Chaos Mesh). 
  * "Убийство" подов в K8s во время транзакции оплаты.
  * Отключение реплик PostgreSQL / Redis.
  * Таймауты внешних API (Литрес, ЮKassa) — проверка паттернов Circuit Breaker и Retry.
* **Критерий завершения:** Система автоматически восстанавливается без потери данных (например, статус заказа не дублируется, деньги не списываются дважды).

#### 3.1.11 Конфигурационное тестирование (Configuration Testing)
* **Цель:** Проверка работы на различных конфигурациях клиентских устройств.
* **Техника:** Тестирование Mobile (Flutter) на различных версиях iOS/Android, с разным объемом RAM (влияние на оффлайн-кэш e-books). Тестирование Web на разных разрешениях и браузерах.

#### 3.1.12 Тестирование установки и обновлений (Installation Testing)
* **Цель:** Проверка процесса установки мобильных приложений и обновления оффлайн-библиотеки.
* **Техника:** Установка из AppStore/Google Play. Тестирование "чистой" установки и обновления "поверх" старой версии. Проверка миграции локального кэша DRM-книг при обновлении приложения.

# Test Plan

## 1. Introduction

### 1.1 Purpose

Настоящий Test Plan для проекта **BookSphere** поддерживает следующие цели:

- Идентифицировать существующую проектную информацию и программные компоненты, подлежащие тестированию.
- Перечислить рекомендуемые Requirements for Test (высокоуровневые).
- Рекомендовать и описать стратегии тестирования.
- Определить необходимые ресурсы и предоставить оценку трудозатрат на тестирование.
- Перечислить результирующие артефакты (Deliverables) тестового проекта.

### 1.2 Background

**BookSphere** — масштабируемая e-commerce платформа нового поколения, предназначенная для продажи печатных книг, электронных книг (e-books) и аудиокниг. Продукт построен по архитектуре Headless Commerce, что позволяет гибко управлять контентом и адаптировать интерфейс под любые каналы продаж (Web, Mobile App, Smart TV, голосовые ассистенты).

Целевая аудитория включает: B2C-покупателей (любители художественной литературы, студенты, родители, профессионалы), B2B-клиентов (библиотеки, образовательные учреждения, HR-департаменты) и внутренних пользователей (контент-менеджеры, маркетологи, операторы колл-центра, сотрудники склада).

Платформа реализована в виде микросервисной архитектуры, упакованной в контейнеры. Frontend включает Web (Next.js / React с SSR/SSG), Mobile (Flutter для iOS и Android), UI/UX (Tailwind CSS, Framer Motion). Backend состоит из микросервисов: Каталог и Поиск (Python FastAPI + Elasticsearch), Корзина и Заказы (Node.js NestJS), Пользователи и Аутентификация (Go Gin + Keycloak), AI и Рекомендации (Python PyTorch / TensorFlow). Headless CMS — Strapi или Sanity. Базы данных: PostgreSQL, Redis, MongoDB, Object Storage (S3), DRM-сервер. Инфраструктура: Yandex Cloud / AWS / Kubernetes, CI/CD через GitLab CI / GitHub Actions, мониторинг через Prometheus, Grafana, ELK Stack, Sentry.

Проект включает внешние интеграции с платёжными шлюзами (ЮKassa, CloudPayments, Stripe), логистическими сервисами (СДЭК, Почта России, Boxberry, Яндекс.Доставка, Shiptor, GotoRoute), ERP/Склад (1С:Предприятие, МойСклад), CRM (Bitrix24 / amoCRM), коммуникационными сервисами (SendGrid, Twilio / SMS.ru, Telegram Bot API) и поставщиками контента (Литрес, Storytel).

## 3. Test Strategy

Test Strategy описывает рекомендуемый подход к тестированию объекта тестирования (target-of-test). Предыдущий раздел (Requirements for Test) описал, **что** будет тестироваться; данный раздел описывает, **как** будет проводиться тестирование.

Для каждого типа тестирования приводятся описание и обоснование. Если тип тестирования не выполняется, это явно указано с обоснованием.

Основные соображения: применяемые техники и критерии завершения тестирования. Тестирование выполняется только с использованием известных, контролируемых баз данных в защищённых средах.

### 3.1 Testing Types

#### 3.1.1 Data and Database Integrity Testing

Базы данных и процессы работы с ними тестируются как подсистемы в рамках проекта BookSphere. Тестирование проводится без пользовательского интерфейса как интерфейса к данным.

| Поле | Описание |
|---|---|
| **Test Objective:** | Обеспечить корректную работу методов доступа к базам данных (PostgreSQL, Redis, MongoDB, Elasticsearch, Object Storage S3) и процессов без повреждения данных. Проверить целостность данных при операциях с каталогом, заказами, пользователями, отзывами, сессиями и корзинами. |
| **Technique:** | • Вызвать каждый метод доступа к БД (микросервисы Каталог/Поиск, Корзина/Заказы, Пользователи/Аутентификация), передавая валидные и невалидные данные или запросы. • Проверить базу данных (PostgreSQL — заказы, пользователи, финансы; MongoDB — отзывы, логи; Redis — кэш, сессии, корзины) для подтверждения корректности записи данных. • Убедиться, что все события БД произошли корректно, или проверить возвращённые данные на предмет корректности выборки. • Проверить целостность данных в Elasticsearch при индексировании и поиске. • Проверить корректность хранения и извлечения объектов в S3 (обложки, фрагменты книг, медиафайлы). |
| **Completion Criteria:** | Все методы доступа к БД и процессы функционируют в соответствии с проектом без повреждения данных. Все записи в PostgreSQL, MongoDB, Redis, Elasticsearch и S3 корректны. |
| **Special Considerations:** | • Тестирование может потребовать среду разработки DBMS или драйверы для прямого ввода/модификации данных. • Процессы вызываются вручную. • Используются базы данных малого или минимального размера (ограниченное число записей) для повышения видимости неприемлемых событий. • Допущение: конкретные инструменты DBMS для прямого доступа не указаны в описании продукта. |

#### 3.1.5 Performance Profiling

Performance Profiling — тест производительности, в котором измеряются и оцениваются времена отклика, скорость транзакций и другие чувствительные ко времени требования. Цель — верифицировать, что требования к производительности достигнуты. Performance Profiling реализуется и выполняется для профилирования и настройки поведения производительности в зависимости от условий (нагрузка, конфигурации оборудования).

Примечание: транзакции ниже относятся к «логическим бизнес-транзакциям» — конкретным use cases, которые пользователь выполняет через платформу (например, поиск книги, оформление заказа, добавление в корзину).

| Поле | Описание |
|---|---|
| **Test Objective:** | Верифицировать поведение производительности для определённых транзакций или бизнес-функций при следующих условиях: • Нормальная ожидаемая нагрузка. • Ожидаемая наихудшая нагрузка. Целевые показатели: время ответа API < 200 мс. |
| **Technique:** | • Использовать Test Procedures, разработанные для Function или Business Cycle Testing. • Модифицировать файлы данных для увеличения числа транзакций или скрипты для увеличения числа итераций каждой транзакции. • Скрипты запускаются на одной машине (наилучший случай для бенчмарка одного пользователя, одной транзакции) и повторяются с несколькими клиентами (виртуальными или реальными). • Ключевые транзакции для профилирования: поиск (Elasticsearch), загрузка карточки товара, оформление заказа, загрузка «Моей библиотеки», получение AI-рекомендаций, работа дашбордов аналитики. |
| **Completion Criteria:** | • Одиночная транзакция / одиночный пользователь: успешное завершение тестовых скриптов без сбоев и в пределах ожидаемого или требуемого выделения времени на транзакцию (< 200 мс для API). • Множественные транзакции / множественные пользователи: успешное завершение тестовых скриптов без сбоев и в пределах допустимого выделения времени. |
| **Special Considerations:** | • Комплексное тестирование производительности включает фоновую нагрузку на сервере. • Методы создания фоновой нагрузки: прямые «драйвовые транзакции» к серверу (SQL-запросы); создание «виртуальной» пользовательской нагрузки (несколько сотен клиентов) с помощью инструментов удалённой терминальной эмуляции; использование нескольких физических клиентов. • Тестирование производительности должно проводиться на выделенной машине или в выделенное время. • Базы данных для Performance Testing должны быть реального размера или пропорционально масштабированы. • Допущение: конкретные инструменты нагрузочного тестирования не указаны в описании продукта. |

Цель — определить и убедиться, что система функционирует корректно за пределами ожидаемой максимальной нагрузки. | **Completion Criteria:** | Множественные транзакции / множественные пользователи: успешное завершение тестов без сбоев и в пределах допустимого выделения времени при нагрузке до 10 000 одновременных пользователей. |
| **Special Considerations:** | • Load Testing должно проводиться на выделенной машине или в выделенное время для полного контроля и точного измерения. • Базы данных для Load Testing должны быть реального размера или пропорционально масштабированы. • Допущение: конкретная инфраструктура для нагрузочного тестирования (число машин, конфигурация) не указана в описании продукта. • Допущение: сценарий пиковой нагрузки (распродажа) не детализирован в описании продукта. |

#### 3.1.7 Stress Testing

Stress Testing — тип теста производительности, реализуемый и выполняемый для обнаружения ошибок из-за нехватки ресурсов или конкуренции за ресурсы. Малый объём памяти или дискового пространства может выявить дефекты, не проявляющиеся в нормальных условиях. Другие дефекты могут возникнуть из-за конкуренции за разделяемые ресурсы (блокировки БД, пропускная способность сети). Stress Testing также используется для идентификации пиковой нагрузки, которую система может выдержать.

| Поле | Описание |
|---|---|
| **Test Objective:** | Верифицировать, что BookSphere функционирует корректно и без ошибок при следующих стрессовых условиях: • Минимальная или отсутствующая память на сервере (RAM и DASD). • Максимальное реальное или физически возможное число подключённых или симулированных клиентов (свыше 10 000). • Множественные пользователи выполняют одинаковые транзакции с одними и теми же данными или аккаунтами. • Наихудший объём или смесь транзакций. Цель: идентифицировать и документировать условия, при которых система НЕ МОЖЕТ продолжать корректно функционировать. |
| **Technique:** | • Использовать тесты, разработанные для Performance Profiling или Load Testing. • Для тестирования ограниченных ресурсов тесты запускаются на одной машине, RAM и DASD на сервере уменьшаются или ограничиваются. • Для остальных стресс-тестов используются множественные клиенты, выполняющие одинаковые или дополняющие тесты для создания наихудшего объёма или смеси транзакций. • Симуляция конкуренции за блокировки в PostgreSQL и Redis. • Симуляция исчерпания места в Object Storage (S3). |
| **Completion Criteria:** | Все запланированные тесты выполнены и указанные системные лимиты достигнуты или превышены без отказа программного обеспечения, либо условия, при которых происходит сбой системы, находятся за пределами указанных условий. |

#### 3.1.9 Security and Access Control Testing

Security and Access Control Testing фокусируется на двух ключевых областях безопасности:

- **Application-level security** — доступ к данным или бизнес-функциям.
- **System-level security** — вход в систему или удалённый доступ.

Application-level security гарантирует, что пользователи ограничены определёнными функциями или use cases, или ограничены в доступных данных. System-level security гарантирует, что только авторизованные пользователи имеют доступ к системе.

| Поле | Описание |
|---|---|
| **Test Objective:** | • **Application-level Security:** Верифицировать, что пользователь может получить доступ только к тем функциям или данным, на которые его тип пользователя имеет разрешения. Типы пользователей: покупатель (B2C), корпоративный клиент (B2B), контент-менеджер, маркетолог, оператор колл-центра, сотрудник склада, администратор. • **System-level Security:** Верифицировать, что только пользователи с доступом к системе и приложениям имеют к ним доступ (аутентификация через Keycloak). • Проверка соответствия: PCI DSS (приём карт), 152-ФЗ / GDPR (защита персональных данных), защита от DDoS и SQL-инъекций. • Проверка DRM-защиты электронных книг. • Проверка защиты фрагмента Look Inside от копирования. |
| **Technique:** | • **Application-level Security:** Идентифицировать и перечислить каждый тип пользователя и функции/данные, на которые каждый тип имеет разрешения. Создать тесты для каждого типа пользователя и верифицировать каждое разрешение путём создания транзакций, специфичных для каждого типа. Модифицировать тип пользователя и повторно запускать тесты для тех же пользователей. Верифицировать, что дополнительные функции или данные корректно доступны или запрещены. • **System-level Access:** Проверка аутентификации через Keycloak, проверка защиты от несанкционированного доступа к API Gateway (Kong / AWS API Gateway). |
| **Completion Criteria:** | Для каждого известного типа пользователя соответствующие функции или данные доступны, и все транзакции функционируют как ожидается и были запущены в предшествующих тестах Application Function. PCI DSS, 152-ФЗ / GDPR требования выполнены. |
| **Special Considerations:** | • Доступ к системе должен быть рассмотрен или обсуждён с соответствующим сетевым или системным администратором. • Допущение: данное тестирование может не требоваться в полном объёме, если является функцией сетевого или системного администрирования. • Допущение: конкретные роли и матрица доступа не детализированы в описании продукта. • Тестирование DRM требует взаимодействия с DRM-сервером и поставщиками контента (Литрес, Storytel). |

#### 3.1.10 Failover and Recovery Testing

Failover and Recovery Testing гарантирует, что объект тестирования может успешно переключиться (failover) и восстановиться (recovery) после различных аппаратных, программных или сетевых сбоев без чрезмерной потери данных или нарушения целостности данных.

| Поле | Описание |
|---|---|
| **Test Objective:** | Верифицировать, что процессы восстановления (ручные или автоматические) корректно восстанавливают базу данных, приложения и систему в желаемое известное состояние. Включаются следующие типы условий: • Отключение питания клиента. • Отключение питания сервера. • Нарушение связи через сетевые серверы. • Нарушение связи, коммуникации или потеря питания к DASD и/или контроллерам DASD. • Незавершённые циклы (прерванные процессы фильтрации данных, прерванные процессы синхронизации данных). • Недействительные указатели или ключи базы данных. • Недействительный или повреждённый элемент данных в базе данных. Контекст BookSphere: микросервисы в Kubernetes (K8s), базы данных PostgreSQL, Redis, MongoDB, Elasticsearch, Object Storage S3, DRM-сервер. SLA 99.9%. |
| **Technique:** | • Тесты, созданные для Function и Business Cycle Testing, используются для создания серии транзакций. | **Completion Criteria:** | Во всех случаях приложение, база данных и система по завершении процедур восстановления возвращаются в известное желаемое состояние. Повреждение данных ограничено известными повреждёнными полями, указателями или ключами. Отчёты указывают процессы или транзакции, не завершённые из-за прерываний. SLA 99.9% соблюдается. |

## 1. Introduction

### 1.1 Purpose

Настоящий тест-план проекта BookSphere определяет:

- состав программных компонентов и сервисов, подлежащих тестированию;
- перечень высокоуровневых требований к тестированию (Requirements for Test);
- стратегии и типы тестирования, применяемые на каждом этапе;
- необходимые ресурсы, роли и оценку трудозатрат;
- перечень артефактов, создаваемых по результатам тестовых активностей.

### 1.2 Background

BookSphere — масштабируемая e-commerce платформа нового поколения для продажи печатных книг, электронных книг (e-books) и аудиокниг. Продукт построен по архитектуре Headless Commerce, что обеспечивает гибкое управление контентом и адаптацию интерфейса под каналы Web, Mobile App, Smart TV и голосовые ассистенты.

Платформа реализована как набор микросервисов в контейнерах под управлением Kubernetes: каталог и поиск (Python/FastAPI + Elasticsearch), корзина и заказы (Node.js/NestJS), пользователи и аутентификация (Go/Gin + Keycloak), AI-рекомендации (Python/PyTorch/TensorFlow). Клиентские приложения: Next.js (Web, SSR/SSG) и Flutter (iOS/Android, оффлайн-режим). Хранение данных распределено между PostgreSQL, Redis, MongoDB, Object Storage (S3) и DRM-сервером.

Платформа интегрирована с платёжными шлюзами (ЮKassa, CloudPayments, Stripe), службами доставки (СДЭК, Почта России, Boxberry, Яндекс.Доставка), ERP/складскими системами (1С:Предприятие, МойСклад), CRM (Bitrix24/amoCRM), каналами коммуникаций (SendGrid, Twilio/SMS.ru, Telegram Bot API) и поставщиками контента (Литрес, Storytel).

Бизнес-модели включают прямые продажи, подписку (безлимитное чтение/прослушивание), маркетплейс с комиссионной моделью и B2B-лицензии для корпоративных библиотек.

### 1.3 Scope

**Стадии тестирования.** Данный план покрывает стадии: модульное (unit), интеграционное (integration), системное (system) и приёмочное (acceptance) тестирование. Типы тестирования: функциональное, производительности, нагрузочное, стрессовое, объёмное, безопасности, отказоустойчивости, конфигурационное, инсталляционное, целостности данных, бизнес-циклов, пользовательского интерфейса.

**Тестируется:**

- Все микросервисы платформы (каталог, корзина/заказы, пользователи, AI-рекомендации);
- Клиентские приложения Next.js (Web) и Flutter (iOS/Android);
- Headless CMS (управление контентом маркетологами);
- Административная панель (PIM, OMS, маркетинг, аналитика);
- Личный кабинет, подписочная модель, маркетплейс, B2B-лицензии;
- Интеграции: платёжные шлюзы, службы доставки, 1С/МойСклад, CRM, коммуникации, поставщики контента;
- DRM-сервер (защита электронных книг);
- Telegram-бот;
- API-контракты для каналов Smart TV и голосовых ассистентов (A6);

**НЕ тестируется (с обоснованием):**

1. Нативные интерфейсы Smart TV и голосовых ассистентов — стек и SDK для этих каналов в описании продукта не заданы; тестирование ограничено уровнем API и headless-контрактов (A6).
2. Физическая логистика и работа курьеров служб доставки — выходит за границы программной системы; тестируется только корректность API-запросов и ответов агрегаторов.

4. Контентная корректность текстов книг, обложек и аудиофайлов — ответственность издательств и поставщиков контента; платформа тестируется на корректность отображения и доставки файлов.
5. Аппаратная производительность клиентских устройств (чипы, дисплеи, динамики) — не относится к программному обеспечению платформы.

A3. DRM-защищённые файлы для тестирования предоставлены поставщиками контента (Литрес, Storytel) в тестовом формате с тестовыми лицензиями.

A4. Нагрузочное и стрессовое тестирование выполняется с генераторами трафика, эмулирующими до 10 000 виртуальных пользователей.

**Риски:**

- Р1. Нестабильность sandbox-окружений внешних интеграций может приводить к простоям тестирования; митигация — локальные wiremock-заглушки.

## 3. Test Strategy

### 3.1 Testing Types

#### 3.1.1 Data and Database Integrity Testing

| Поле | Содержание |
|---|---|
| **Test Objective** | Убедиться, что методы доступа и процессы во всех хранилищах (PostgreSQL, Redis, MongoDB, S3, DRM-сервер) функционируют корректно и без повреждения данных при штатных и нештатных операциях. |
| **Technique** | Вызвать каждый метод доступа к БД (CRUD-операции сервисов каталога, заказов, пользователей, рекомендаций), передавая валидные и невалидные данные. Проверить: записи в PostgreSQL соответствуют ожидаемым; кэш Redis инвалидируется корректно; документы MongoDB не содержат осиротевших ссылок; объекты в S3 сохраняются с верным checksum; DRM-ключи не повреждаются при повторном шифровании. Инспектировать БД после каждой операции и сравнивать возвращённые данные с эталонными. |

По результатам тестирования создаются и поддерживаются в TestRail:

- Отчёты по выполнению тест-ранов для каждого цикла (MVP, Full, QA).

### 6.2 Test Logs

Результаты тестирования фиксируются:

- Ручные тесты: логирование в TestRail с привязкой к тест-рану, статусы (Passed / Failed / Blocked / Not Run), фактические результаты, скриншоты/видео;

- Нагрузочные тесты: дашборды Grafana с временны́ми рядами (латентность, RPS, ошибки, ресурсы), экспортируемые в PDF по завершении прогона;
- Статус тестирования еженедельно: сводка в Confluence (% выполнения, блокеры, риски).

### 6.3 Defect Reports

- Регистрация и отслеживание дефектов: Jira (проект `BOOKSPHERE`, тип «Bug»). Поля: severity (Critical / High / Medium / Low), приоритет, компонент (микросервис), окружение, шаги воспроизведения, ожидаемый/фактический результат, логи и скриншоты;
- Еженедельный отчёт по дефектам: распределение по severity, статусу, возрасту; метрики: open rate, fix rate, reopen rate;
- Критерии закрытия цикла: 0 открытых Critical; ≤ 3 открытых High с утверждённым workaround; ≤ 10 открытых Medium; дефекты Low переносятся в бэклог продукта.

# 1. Введение

## 1.1 Цель

Тест-план BookSphere определяет:

- компоненты, каналы продаж, интеграции и бизнес-модели, подлежащие проверке;
- высокий уровень требований к тестированию и 48 сценариев использования;

- вехи и тестовые циклы внутри этапов MVP и Full-версии, а не только в выделенном QA-месяце;
- передаваемые артефакты: тестовую модель, журналы тестирования и отчёты о дефектах.

## 1.2 Предпосылки

BookSphere — масштабируемая e-commerce платформа для продажи печатных книг, электронных книг и аудиокниг. Архитектура Headless Commerce разделяет контент и торговую логику на сервере и каналы представления: Next.js для Web и Flutter для iOS/Android. Микросервисы упакованы в контейнеры и оркестрируются Kubernetes: каталог и поиск на Python/FastAPI с Elasticsearch, корзина и заказы на Node.js/NestJS, пользователи и аутентификация на Go/Gin с Keycloak, AI-рекомендации на Python/PyTorch/TensorFlow.

Платформа обслуживает покупателей B2C, корпоративных клиентов B2B (библиотеки, образовательные учреждения, HR-департаменты) и внутренних пользователей: контент-менеджеров, маркетологов, операторов колл-центра и сотрудников склада. Бизнес-модели включают прямые продажи, подписку «Все включено», маркетплейс с комиссией сторонних продавцов и корпоративные B2B-лицензии. Уникальные возможности — книжные клубы, голосовые рецензии, публичные полки, AR-витрина, эко-трекинг и гибридный ридер с Immersion Reading.

Данные разделены по назначению: PostgreSQL хранит заказы, пользователей и финансы; Redis — кэши, сессии и корзины; MongoDB — отзывы и логи; S3 — обложки, фрагменты и медиа; DRM-сервер защищает электронные книги. Внешний контур образуют платёжные шлюзы, службы доставки, ERP/склад, CRM, коммуникации и поставщики контента. Нормативные ориентиры платформы: API < 200 мс, до 10 000 одновременных пользователей, SLA 99,9%, PCI DSS, 152-ФЗ / GDPR и автоматическое горизонтальное масштабирование.

### Допущения A1–A10

- **A1.** Целевой контур разворачивается в Yandex Cloud на Kubernetes; API Gateway — Kong, Headless CMS — Strapi. Альтернативы из описания (AWS API Gateway, Sanity) в тестовый контур не включаются.
- **A2.** Вход выполняется учётной записью Keycloak (логин и пароль). Способы входа, не перечисленные в описании продукта, не реализуются в тест-модели и не тестируются.
- **A3.** Базовый набор данных: 45 000 SKU (20 000 произведений в доступных форматах), 50 000 пользователей, 1 000 000 заказов. Volume-набор — тот же профиль, умноженный на 10: 450 000 SKU и 10 000 000 заказов. Такой объём позволяет проверять фильтры, пагинацию, отчёты и индексы без переноса боевых данных.
- **A4.** Платежи, логистика, ERP, CRM, коммуникации и поставщики контента проверяются через sandbox и контрактные mock-адаптеры. Боевые списания и внешние боевые контуры не используются.
- **A5.** Роли «продавец маркетплейса» и «корпоративный администратор B2B» обслуживаются Back-office. Матрица прав всех ролей фиксируется в тестовой модели и является основанием для проверок доступа.
- **A6.** Нагрузочный контур ST-PERF разворачивается в полном целевом размере. Подтверждение 10 000 одновременных пользователей не экстраполируется с уменьшенного стенда.
- **A7.** SLA 99,9% измеряется скользящим годовым окном. Для тестового 30-суточного цикла применяется пересчёт: не более 43,2 мин недоступности, из которых плановые окна — не более 40 мин (8 часов простоя в год на плановые работы, распределённые по месяцам).

- **A10.** Календарь плана: 22 рабочих дня в месяце. Этапы MVP и Full длятся по 4 месяца и содержат по 4 месячных релизных цикла; внутри каждого месяца — две двухнедельные итерации. Поддержка после релиза включена в объём плана на 0,5 месяца.

# 3. Стратегия тестирования

Стратегия риск-ориентированная и многоконтурная. Компонентные и контрактные проверки выполняются в CI каждой двухнедельной итерации; системные и сценарные прогонки — в конце каждого месячного релизного цикла MVP и Full; специальный контур нагрузки, хаоса и безопасности работает в M13. Основные техники: black-box по use cases, контрактное тестирование API и headless-контента, state-based проверка хранилищ, chaos engineering и модельное тестирование бизнес-циклов.

Все работы выполняются только на известных управляемых наборах данных (A3) в изолированных защищённых контурах. Боевые персональные данные не используются.

**Единый дефект-гейт (рекомендуемый):** 0 открытых дефектов С1 и С2; не более 10 открытых С3, каждый с обходным путём и планом исправления; С4 регистрируются без блокировки релиза. Классификация: С1 — потеря данных, недоступность платформы или утечка ПД; С2 — неработающий бизнес-сценарий без обхода; С3 — сценарий работоспособен с обходом; С4 — косметические недостатки.

Числовые значения, не взятые из Описания продукта, помечены словом «рекомендуемый». Порог API < 200 мс измеряется на API Gateway и относится ко всем сервисам; клиентские сетевые задержки в этот бюджет не входят.

## 6.1 Тестовая модель

- профиль нагрузочных транзакций 40/20/20/15/5;
- матрица конфигураций Web/Mobile и сценариев развёртывания.

## 6.2 Журналы тестирования

Владельцы — Tester, Mobile QA, Performance QA, Security QA. Ведутся в TestRail для сценарных прогонов, в CI для компонентных и контрактных проверок, в Grafana для нагрузочных и SLA-наблюдений.

В журнале фиксируются идентификатор UC, идентификатор стенда, версия набора данных, время прогона, результат по шагам, приложенные логи и скриншоты, ссылка на профиль производительности. Хранение — 12 месяцев (рекомендуемый срок). 30-суточный журнал доступности хранится вместе с результатом failover-тестов как основание для приёмки SLA 99,9%.

## 6.3 Отчёты о дефектах

Владелец — Test Manager; заведение и актуализация — все исполнители. Система учёта — Jira.

Обязательные поля: severity (С1–С4), связка с UC, стенд, набор данных, шаги воспроизведения, ожидаемый и фактический результат, вложение, статус, план исправления.

Реакция на дефекты (рекомендуемые сроки): С1 — 4 часа, С2 — 1 рабочий день, С3 — 5 рабочих дней, С4 — план ближайшей итерации.

Отчёт о цикле содержит число выполненных и пройденных кейсов, покрытие UC и кода, распределение дефектов по severity, список открытых С3 с обходными путями и вывод о соответствии критериям завершения. Приёмка релиза возможна только при выполнении единого дефект-гейта и типовых критериев разделов 3.1.1–3.1.12.
