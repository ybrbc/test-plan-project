# Итоги анализа тест-планов BookSphere

## Цель работы

В работе разобраны тест-планы для платформы BookSphere, составленные по трём шаблонам: IEEE 829-1998, Rational Unified Process (RUP) и русскоязычному шаблону «План тестирования». Для каждого стандарта проведено сравнение нескольких итераций документа, выявлены структурные и содержательные ошибки, а также составлен перечень необходимых правок.

Оценки в таблицах ниже — это экспертная проверка самих текстов по десяти критериям соответствующего разбора. Они отражают качество документации, но не заменяют реального тестирования BookSphere и не доказывают общее превосходство какой-либо языковой модели.

## Итоги по шаблонам

### IEEE 829-1998

Лучший результат показал **Ответ 4 — 42/50**. В нём сохранены все 16 разделов стандарта, закрыты пробелы предыдущих итераций по охвату функций, отдельно расписаны проверки DRM, AI-рекомендаций (с порогом `< 200 мс`), платежей и безопасности. Сведена арифметика по задачам (42 задачи на 842 чел.-дня для команды из 8 специалистов), а доля высокоприоритетных требований (`High`) удержана в пределах трети (8 из 28 функций — 28,6%).

При этом из-за большого объёма документа в Ответе 4 накопились внутренние нестыковки и точечные пропуски:
- в разделе 10 в итоговый текст попали служебные расчёты и комментарии модели («Проверка загрузки по месяцам» и «Корректировка по Discovery»);
- логистика описана через прямые API перевозчиков без упоминания агрегаторов Shiptor и GotoRoute, а в F27 упущена диалоговая часть Telegram-бота-ассистента (оставлены только уведомления);
- пропали обязательные для стандарта `Test Item Transmittal Reports` (§9) и браузерная матрица для Web-клиента (§6.5), которые присутствовали в третьей версии;
- для unit-тестов и эмуляторов внешних сервисов не назначены исполнители и задачи, указана неподтверждённая версия `Elasticsearch 8.x`, а между разделами 9, 10, 11 и 12 есть расхождения в названиях этапов, числе мобильных устройств (8 против 10) и распределении ролей.

**Решение:** принять Ответ 4 за основу. Переписывать промпт в пятый раз нецелесообразно — при таком объёме текста модель начинает терять перекрёстные ссылки, поэтому оставшиеся замечания быстрее устранить ручной правкой.

### RUP

Лучший результат получила **Версия 3 — 47/50**. Документ полностью сохраняет структуру шаблона RUP (6 основных глав, Приложение A и 24 подраздела, включая 12 подразделов видов тестирования `3.1.1`–`3.1.12`), а также содержит критерии входа/выхода, матрицы Severity/Priority, жизненный цикл дефекта и реестр рисков. К третьей итерации из плана удалили выдуманные спецификации в §1.4 и неподтверждённые версии СУБД, обновили список мобильных и десктопных ОС под актуальные на 2026 год платформы, выровняли число рабочих станций (11 ноутбуков под 10,5 FTE) и перенесли контрольные точки на пятницы.

Трудозатраты полностью сбалансированы: 202 чел.-дня основной работы и 8 чел.-дней буфера (всего 210 чел.-дней). Недельная загрузка распределена как `50 + 52 + 50 + 50` чел.-дней и нигде не превышает пятидневный лимит команды (52,5 чел.-дня).

Недочётов в самом документе осталось минимум: интеграция с Telegram сведена только к рассылке уведомлений через Bot API без детализации сценариев диалогового бота-ассистента, а в разделе 1.2 сохранилась мелкая опечатка («хранит обложек»).

**Решение:** использовать Версию 3 как итоговую основу документа после дополнения сценариев для Telegram-бота и исправления опечатки в §1.2.

### Русский шаблон («План тестирования»)

В основное сравнение вошли три последние итерации из шести (после промптов 4, 5 и 6 в `DeepSeek`). Лучший результат получил **План C — 39/50**, опередив План A (34/50) и План B (30/50). В Плане C полностью согласованы диаграмма, матрица переходов, граф, таблица из 16 действий и статусы Jira для жизненного цикла дефекта (§6.4), сошлась сумма трудозатрат (246 чел.-дней в §7.2), вернулись потерянные в версии B нефункциональные проверки и устранены выдуманные ссылки на разделы `task.md`.

При этом План C рассматривается как **база для финальной сборки**, которую нужно дополнить удачными решениями из двух предыдущих версий:
- из **Плана A** стоит перенести подробную аппаратную конфигурацию со схемой окружений в Mermaid (§4.2) и измеримые пороги в §6.4.7;
- из **Плана B** — явные пометки `Допущение` и единую шкалу оценки рисков.

Дополнительно при подготовке итоговой редакции нужно добавить пропущенное во всех версиях оглавление, пометить проектные документы в §2.4 и §7.1 как планируемые, заменить перенесённый из шаблона пример имени (`Natallia Hustyr` в §6.4.8), добавить в журнал тестирования (§9.1) статусы `Blocked` и `Not Run`, а в §3.2 учесть зависимость AR-витрины от партнёрского офлайн-магазина.

**Решение:** собрать итоговый документ на базе Плана C по составленной таблице слияния (раздел 6 профильного анализа) и провести финальную вычитку.

## Общие выводы по работе с промптами и шаблонами

1. **В рассмотренных итерациях последовательные точечные правки сработали лучше длинных промптов с самопроверкой.** По всем шаблонам оценки росли от начальных версий к финальным (IEEE: `26 → 42`, RUP: `36 → 47`, русский шаблон: `34 → 30 → 39`). При этом падение оценки Плана B в русском шаблоне (с 34 до 30 баллов) и появление лишних служебных блоков в Ответе 4 по IEEE показали, что перегруженный промпт со встроенным чек-листом самопроверки может приводить к сжатию текста и потере целых разделов. Более предсказуемый результат дала базовая генерация каркаса с последующими короткими запросами по конкретным замечаниям.
2. **Соблюдение структуры шаблона не исключает фактических ошибок внутри разделов.** Модель точно воспроизводит оглавление из 16 разделов IEEE или структуру RUP из 6 глав и 24 подразделов, но внутри таблиц может указывать несуществующие документы (`SRS v2.4`, `BookSphere_Project_Plan.mpp`), выдумывать номера разделов ТЗ (`5.5`, `7.4` в Плане A) или механически переносить примеры из исходного шаблона (`ClearQuest`, `Natallia Hustyr`).
3. **Инженерные решения нужно явно отделять от фактов ТЗ.** Паспорт `task.md` задаёт верхнеуровневые ориентиры (API `< 200 мс`, `10 000` пользователей, `SLA 99,9%`), но не фиксирует версии СУБД, профиль нагрузки, число нод в кластере или процент покрытия кода. Наиболее наглядный способ оформить такие решения применялся в RUP (общая оговорка на титульном листе) и в IEEE (выделенный блок допущений `A1–A10`), тогда как пометки в каждой ячейке таблицы (Ответ 2 в IEEE) перегружают текст и мешают конкретизировать план.
4. **Сквозная арифметика и роли — наиболее уязвимое место при генерации объёмных планов.** При исправлении таблицы задач в одном разделе легко нарушается согласованность цифр в графике, списке оборудования или матрице ответственности (например, 6 ноутбуков на 11 человек в RUP В1, сроки 10–12 недель против 46 недель в Плане A, либо появление в разделе рисков ролей DevOps и Security, которые не описаны в составе команды).
5. **Составные требования из описания продукта часто покрываются лишь частично.** В разборах по шаблонам IEEE и RUP зафиксирована одна и та же ошибка при переносе требования `Telegram Bot API (бот-ассистент и уведомления)`: планы предусматривали проверку уведомлений, но упускали сценарии работы самого диалогового бота-ассистента (команды, диалоги, права доступа). Аналогично в русском шаблоне при переносе функции AR-витрины терялась её привязка к партнёрскому офлайн-магазину.

## Вопросы к заказчику перед стартом тестирования

Ни один тест-план не может закрыть пробелы исходного паспорта продукта. Перед реальным запуском тестирования с владельцем продукта и архитектором необходимо согласовать:

| Область | Что требуется уточнить |
|---|---|
| Производительность API | Для какого процентиля (`p95`, `p99` или среднее), на каких эндпоинтах и в какой точке сети измеряется порог `< 200 мс` |
| Профиль нагрузки | Как трактуются `10 000 одновременных пользователей` (число активных сессий или RPS), каков `think time` и длительность удержания пика |
| SLA 99,9% и техработы | Входят ли 8 часов плановых работ в годовой бюджет простоя (0,1% от года — это 8 ч 45 мин) и как оценивать выполнение SLA в рамках этапа тестирования |
| Безопасность и аудит | Где проходит граница между внутренним тестированием безопасности силами QA и внешним сертифицированным аудитом по PCI DSS и 152-ФЗ/GDPR |
| Внешние интеграции | Доступны ли тестовые среды (sandbox) платёжных шлюзов, агрегаторов Shiptor и GotoRoute, 1С и поставщиков цифрового контента, либо требуется разработка собственных mock-сервисов |
| Матрица платформ | Точные версии поддерживаемых браузеров и мобильных ОС, а также статус клиентских приложений для Smart TV и голосовых ассистентов в текущем релизе |
| Ресурсы и график | Фактический состав команды, длительность этапа релиза и объём временного резерва на повторную проверку исправленных дефектов |

## Ограничения проведённого анализа

- Все оценки выставлены экспертно по критериям соответствующих разборов.
- Планы создавались в разных диалогах, по разным шаблонам и за разное число шагов, поэтому работа показывает динамику доработки документации, а не строгое сравнение возможностей нейросетей.
- Проверялась только текстовая документация: исходный код, рабочие сборки, API-контракты и тестовые стенды BookSphere отсутствуют.
- Для русского шаблона План C зафиксирован как основа со списком обязательных доработок; считать его завершённым документом можно только после их внесения.

## Заключение

По итогам трёх разборов выбраны наиболее качественные основы для подготовки тестовой документации по каждому стандарту: **Ответ 4 для IEEE 829-1998 (42/50), Версия 3 для RUP (47/50) и План C для русского шаблона (39/50)**. Перед практическим использованием в Версии 3 по RUP и Ответе 4 по IEEE достаточно устранить оставшиеся локальные замечания, тогда как План C по русскому шаблону требует предварительной сборки с включением удачных блоков из версий A и B. При этом переход к реальному тестированию по любому из планов возможен только после согласования открытых вопросов с заказчиком.

Помимо выбора лучших вариантов, проделанная работа выявила типичные ошибки языковых моделей при проектировании QA-документации: выдумывание артефактов и версий ПО, подмену понятий в нагрузочном тестировании, потерю отдельных компонентов составных требований и рассинхронизацию таблиц в длинных документах.
