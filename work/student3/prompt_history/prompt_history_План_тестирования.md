## 5. Стратегия тестирования

Основной метод — ручное функциональное тестирование «чёрного ящика» на основе требований. Дополняется автоматизированным, техническим и специализированными видами тестирования.

### 5.1 Функциональное тестирование
- **Smoke-тест (МПТ):** ежедневно/при каждой сборке, проверка критических путей (регистрация, вход, поиск, добавление в корзину, оформление заказа, оплата, доступ к «Моей библиотеке», админ-панель). Длительность ≤ 1 часа.
- **Регрессионное тестирование:** после каждого исправления дефектов и перед релизом — повторное прохождение тест-кейсов предыдущих итераций.
- **Функциональный тест:** полное покрытие тест-кейсами всех модулей, включая граничные значения, специальные символы, нестандартное использование, бизнес-процессы, логические цепочки, взаимодействие функций, корректность обновления и отображения данных.

### 5.2 Автоматизированное тестирование
- **API-тесты:** проверка контрактов микросервисов, кодов ответов, валидации, аутентификации/авторизации (Keycloak), интеграций.
- **UI-тесты:** критические пользовательские сценарии (Playwright/Cypress) для веб, интеграция в CI/CD.
- **Нагрузочные тесты:** сценарии с использованием Locust/JMeter, эмуляция до 10 000 одновременных пользователей, замер времени отклика API (<200 мс), проверка авто-масштабирования.
- **Автоматизация регрессии:** приоритетные тест-кейсы.

### 5.3 Техническое тестирование
- **Нагрузочное:** пиковые нагрузки (распродажи), проверка SLA 99.9%, отказоустойчивость.
- **Производительность:** время ответа API, рендеринг страниц (SSR/SSG), работа поиска (Elasticsearch), мобильного приложения.
- **Стресс-тестирование:** критические условия (нехватка ресурсов, отказ узлов K8s), восстановление.
- **Тестирование больших объемов данных:** каталог (миллионы книг), история заказов, отзывы.
- **Безопасность:** проверка PCI DSS (платежи), 152-ФЗ/GDPR (персональные данные), защита от DDoS, SQL-инъекций, XSS, CSRF; тестирование DRM (защита контента); аудит аутентификации/авторизации (Keycloak).
- **Совместимость:** браузеры (Chrome, Firefox, Safari, Edge), мобильные устройства (iOS/Android), разрешения экранов.
- **Мобильное тестирование:** нативные функции (аудиоплеер, оффлайн-режим, AR, эко-трекинг), синхронизация прогресса, push-уведомления.
- **Юзабилити-тестирование:** экспертная оценка ключевых сценариев (поиск, оформление заказа, личный кабинет, админ-панель).

### 5.4 Тестирование интеграций
- Проверка каждого внешнего API (платежи, логистика, ERP, CRM, коммуникации, поставщики контента) в тестовых средах, обработка ошибок, таймаутов, повторных попыток.

### 5.5 Тестирование документации
- Проверка руководства пользователя, инструкций для администраторов, онлайн-справки.

## 6. Методология тестирования

### 6.1 Обзор процесса
1. Получение требований (паспорт, ТЗ).
2. Анализ требований, определение целей и задач тестирования.
3. Разработка тестовой документации (план, тест-кейсы, сценарии, наборы данных).
4. Установка очередной версии на тестовое окружение.
5. Smoke-тест → решение о допуске к дальнейшему тестированию.
6. Регрессионное тестирование (проверка исправлений).
7. Полный цикл функционального тестирования, регистрация дефектов.
8. Техническое и автоматизированное тестирование (по расписанию).
9. Тестирование документации.
10. Предоставление отчета о качестве заказчику.
11. Исправление дефектов разработчиками.
12. Сборка новой версии, нотификация команды тестирования.
13. Анализ изменений, актуализация тестовой документации.
14. Повторный цикл (п. 4).
15. При кандидат-релизе — полное приемо-сдаточное тестирование.

### 6.2 Тестовая документация
- План тестирования (настоящий документ).
- Сценарии тестирования (Excel/Word) — по модулям.
- Тест-кейсы (детальные) — для функционального и автоматизированного тестирования.
- Наборы тестовых данных.
- Журнал тестирования (Excel).
- Матрица трассировки требований.
- Отчеты о дефектах.
- Итоговый отчет о качестве.

### 6.3 Доставка новых версий
- Новые версии размещаются в GitLab CI/CD (артефакты) или на FTP заказчика.
- Каждая версия сопровождается e-mail нотификацией с номером версии и списком изменений.
- Перед началом тестирования статусы дефектов в трекере должны быть актуальны (исправленные — переведены в Resolved с указанием сборки).

**Критерии приемки версии на тестирование:**
- Наличие изменений.
- Отсутствие блокирующих дефектов, делающих невозможным тестирование большей части функциональности.
- Доступность версии для установки.

### 6.4 Управление дефектами

**Инструмент:** Jira (или аналогичная система, например, YouTrack). Выбор обусловлен поддержкой Agile, интеграцией с CI/CD и удобством отчетности.

#### 6.4.1 Степени важности (Severity)
- **Критический (Critical):** блокирует большую часть функциональности, полностью нерабочая функция, потеря информации.
- **Серьезный (Major):** некорректная работа части функциональности, недоступность опций, блокирующая ошибка отдельной функции без влияния на систему.
- **Средний (Average):** неправильная работа неосновной части функциональности, есть обходные пути.
- **Незначительный (Minor):** косметические ошибки, не нарушающие бизнес-логику.

#### 6.4.2 Приоритеты (Priority)
- **Resolve immediately** — наивысший, исправить в кратчайшие сроки.
- **Give high attention** — повышенное внимание, устранить в ближайшее время.
- **Normal queue** — обычный (по умолчанию).
- **Low priority** — низкий, после всех остальных.
- **Enhancement** — предложение по улучшению (после валидации заказчиком).

#### 6.4.3 Жизненный цикл дефекта
`Submitted → Opened → Resolved → Closed` (с возможными переходами в `Reopened`, `Postponed`, `Duplicate`).  
Матрица переходов и ответственные лица — согласно корпоративному регламенту (аналогично приведенному в шаблоне).

#### 6.4.4 Регистрация дефектов
Обязательные поля: ID, Статус, Заголовок, Ответственное лицо (Owner), Важность (Severity), Приоритет, Модуль, Группа, Функция, Версия сборки, Компонент исправления, Описание (шаги воспроизведения, ожидаемый/фактический результат), Вложения (скриншоты, логи).

#### 6.4.5 Критерии качества продукта
- Соответствие спецификациям и требованиям.
- Полное покрытие функциональности, запланированной на итерацию.
- Отсутствие известных дефектов со статусом «Критический» и «Серьезный» к моменту поставки заказчику.

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ
Основным методом проверки данного программного продукта будет ручное функциональное тестирование с использованием метода «черного ящика», который базируется на использовании требований и спецификаций, и не предполагает наличия каких-либо специальных знаний о конфигурации и внутренней структуре объекта испытаний. В процессе тестирования BookSphere будут применяться следующие его типы:

### 5.1 Функциональное тестирование
Функциональное тестирование – это процесс тестирования программного продукта на предмет соответствия требованиям к программному продукту и правильности реализации всех характеристик, заложенных в продукт. Осуществляется вручную функциональным тестировщиком. Данный вид тестирования будет включать в себя два этапа:

#### 5.1.1 Минимальный приемочный тест (Smoke test).
МПТ – это короткий тест, проверяющий основную функциональность программного продукта и его работоспособность, длящийся не более 1 часа. По результатам приемочного теста принимается решение о допуске версии программного продукта к дальнейшему тестированию.
Для BookSphere МПТ включает: авторизацию, работу каталога и поиска (Elasticsearch), добавление товара в корзину, оформление заказа, переход в личный кабинет, доступ к админ-панели.
Если очередная версия программного продукта не прошла приемочный тест, то по его результатам может быть принято решение о дальнейшем частичном тестировании программного продукта. Минимальный приемочный тест будет выполняться для каждой из поставленных версий продукта. Основная его задача – это оперативное отслеживание регрессии качества и получение высокоуровневой картины работоспособности продукта.

#### 5.1.2 Регрессионное тестирование.
Для обеспечения надлежащего качества продукта на каждом последующем этапе будет производиться регрессионное тестирование функциональности, разработанной на предыдущей стадии и ее совместимости с новой функциональностью. Регрессионное тестирование подразумевает под собой повторное прохождение всех тестовых случаев протестированных после завершения предыдущего этапа разработки системы, проверки исправления дефектов, допущенных на этом этапе разработки системы, неповлияния новых, корректное взаимодействие и совместимость функций.

#### 5.1.3 Функциональный тест.
Функциональный тест – основной вид теста, во время которого проверяются основная функциональность программного продукта при стандартном его использовании, а также проверяется нестандартное использование программного продукта, границы переполнения массивов данных, ввод специальных символов и т.п. Для проведения функционального теста используется весь объем созданной тестовой документации. Особое внимание уделяется тестированию бизнес-процессов системы (жизненный цикл заказа, применение промокодов, списание бонусов, оформление подписки), логических цепочек последовательностей действий пользователей (от поиска книги до оплаты и синхронизации в «Моей библиотеке»), взаимодействие функций системы между собой (PIM -> Каталог -> Витрина), корректное обновление и отображение данных.

### 5.2 Автоматизированное тестирование.
Основной целью автоматизации тестирования является решение сложных задач, выполнение которых не может быть осуществлено вручную в рамках сжатых сроков при минимальном привлечении ресурсов.
Автоматизированное тестирование подразумевает под собой использование специального программного обеспечения для проведения автоматизированных тестов на основе набора тестовых данных и написанных скриптов. Осуществляется разработчиком автоматизированных тестов.
В рамках BookSphere автоматизация будет направлена на регрессионное тестирование API-микросервисов (FastAPI, NestJS, Go), сквозные сценарии (E2E) на Playwright для Web (Next.js) и интеграцию автотестов в CI/CD (GitLab CI / GitHub Actions).

### 5.3 Техническое тестирование
Техническое тестирование имеет своей основной целью проверку нефункциональных требований, предъявляемых к программному продукту, будет осуществляться с использованием прикладного программного обеспечения (Apache JMeter, Locust) и производится техническим тестировщиком.
Данный вид тестирования включает в себя несколько типов тестов:
* **Нагрузочное тестирование** - проверка работоспособности системы при одновременной работе до 10 000 пользователей (имитация пиковых нагрузок во время распродаж);
* **Тест производительности** - проверка быстродействия работы системы, времени отклика API (требование: < 200 мс), времени загрузки страниц (SSR/SSG);
* **Тестирование работоспособности системы при больших объемах данных** (проверка функционирования Elasticsearch, БД при обработке массива книг и отзывов);
* **Стресс-тесты** - проверка работоспособности системы в критических условиях и проверка механизмов Auto-scaling в Kubernetes;
* **Тестирование безопасности** - проверка защиты от DDoS, SQL-инъекций, соответствие PCI DSS и 152-ФЗ, проверка работы DRM-сервера;
* **Восстановление работоспособности системы при сбоях** (отказоустойчивость микросервисов).

Подробное описание этапов проведения технического тестирования приведено в документе [4].

### 6.3 Доставка новых версий программного продукта

#### 6.3.1 Процесс доставки
Новые версии продукта должны выкладываться посредством CI/CD пайплайна (GitLab CI / GitHub Actions) в тестовую среду (Staging).
Каждая новая версия должна сопровождаться e-mail нотификацией (или уведомлением в Telegram-боте) на проектную команду с указанием:
* номера версии продукта;
* произведенных изменений (Release Notes).
К моменту начала проведения повторного цикла тестирования разработчики должны привести состояния дефектов в дефект-трекинговой системе в актуальное состояние (исправленные дефекты должны быть отправлены на валидацию, владельцами дефектов должны стать тестировщики, осуществившие регистрацию дефектов).

#### 6.3.2 Критерии приемки на тестирование
Тестирование новой версии программного продукта может быть отложено полностью или частично в одном из следующих случаев:
* В новой версии программного продукта не было внесено никаких изменений;
* Программный продукт содержит ошибки, которые не позволяют провести тестирование большей части функциональности (например, недоступен API Gateway или не работает база данных);
* Новая версия программного продукта не доступна для тестирования (сбой деплоя).

### 6.4 Управление дефектами
Средством регистрации и отслеживанием текущего состояния дефектов для данного проекта выбран инструмент **Jira** (или ClearQuest от Rational Software, в зависимости от инфраструктуры Заказчика).
Данный продукт будет установлен локально или предоставлен доступ через Web.

#### 6.4.1 Определение степени важности дефектов
Важность дефекта (Severity) требуется для правильной оценки степени влияния дефекта на корректность выполнения операций конечным пользователем.
Различают следующие степени важности дефектов:
* **«Критический» (Critical)** – дефект, блокирующий большую часть функциональности, полностью нерабочая функция (например, не работает оплата, не открывается каталог), ветвь функциональности или дефект, приводящий к потере информации (потеря заказов, утечка персональных данных);
* **«Серьезный» (Major)** – дефект, приводящий к некорректной работе части функциональности, недоступности опций отдельной функции (например, не применяется промокод), но не блокирующий тестирование в целом. Также это может быть блокирующая ошибка для отдельной функции, не оказывающей влияния на работу всей системы;
* **«Средний» (Average)** – ошибка характеризуется неправильно работающей неосновной части функциональности, не препятствующая проведению тестирования (т.е. присутствуют методы альтернативного доступа к функциям и их опциям);
* **«Незначительный» (Minor)** – приложение может успешно функционировать, не нарушена бизнес-логика, исправление дефекта откладывается на последнюю очередь (например, опечатка в тексте, кривой отступ).

#### 6.4.2 Определение приоритета дефектов
Приоритет дефекта определяется, чтобы правильно оценить, насколько срочно требуется исправление дефекта.
Приоритет должен быть основан на:
* Серьезности дефекта.
* Критичности функции для пользователя.
Различают следующие приоритеты:
* **«Исправить незамедлительно» (Resolve immediately)** – исправление дефекта имеет наивысший приоритет, должно быть осуществлено в первую очередь в кратчайшие сроки.
* **«Уделить повышенное внимание» (Give high attention)** – нет необходимости в сверхсрочном исправлении дефекта, но устранение ошибки должно быть осуществлено непосредственно.
* **«Обычный» (Normal queue)** – дефолтный приоритет при регистрации дефектов.
* **«Низкий» (Low priority)** – дефекты исправляются только после устранения всех других ошибок в программе.
* **Улучшение (Enhancement)** – предложения тестовой группы по улучшению качества интерфейса (внедряется только после валидации заказчиком).

* Дефект несущественный и не требует исправления (не нарушены бизнес-требования);
* Коррекция дефекта нецелесообразна - исправление дефекта окажет критическое действие на большую часть функциональности (предложение варианта по изменению требований к продукту).

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой.
* При регистрации дефекта он приобретает статус Submitted (регистрируется тестировщиками) – выставляется owner дефекта – лидер команды тестирования;
* Лидер команды тестирования проверяет воспроизведение дефекта и открывает его на лидера команды разработчиков (дефект приобретает статус Opened);
* Лидер команды разработчиков квалифицирует дефект и назначает ответственного за его исправление разработчика (action = Modify), редактируется значение только поля Owner, как правило это разработчик функции (дефект остается в состоянии Opened). В системе автоматически формируется и отсылается нотификация ответственному лицу;
* Разработчик после исправления дефекта проставляет версию билда, в котором будет доступен фикс для тестирования, выбирает action = Resolve, назначается owner = тестировщик, осуществивший регистрацию дефекта, дефект переходит в состояние Resolved;
* Тестировщик проверяет исправление дефекта, в случае если дефект исправлен корректно - вызывает action = Validate, дефект переходит в состояние Closed. Если дефект не исправлен или исправлен частично, тестировщик вызывает action = Reject (указывает в поле Notes номер версии билда, в котором дефект был оттестирован, описывает проблемы, почему дефект не исправлен), проставляется owner = разработчик, осуществлявший исправление, дефект снова переходит в состояние Opened. Цикл повторяется.
* На всех промежуточных этапах дефект можно редактировать (action = Modify), это действие не изменяет статуса дефекта, но сохраняет изменения и комментарии.
* Лидер команды разработчиков может закрывать дефект (action = Close) с выставлением резолюций. Исправление дефекта по разным причинам может быть отложено – action = Postpone (state = Postponed). В случае если подобный дефект уже был зарегистрирован, ему присваивается статус Duplicate.
* В случае если дефект не воспроизводится у разработчиков, недостаточно подробно описан процесс воспроизведения или не ясен общий смысл ошибки, лидер команды разработчиков выставляет Owner = тестировщик, осуществивший регистрацию, и пишет письмо с перечнем вопросов. Тестировщик дополняет дефект в трекере необходимыми комментариями, выставляет Owner = лицо, запросившее дополнительную информацию и нотифицирует почтой.

Перечень необходимых для заполнения полей при регистрации дефекта приведен в следующей таблице:

| Название поля | Описание | Перевод |
| :--- | :--- | :--- |
| **ID** | Идентификационный номер дефекта, заполняется автоматически системой | ID |
| **Статус** | Текущее состояние дефекта | State |
| **Заголовок** | Название дефекта (краткое описание – привязка дефекта к функции) | Headline |

| **Важность** | Серьезность дефекта, определяется для правильной оценки степени влияния дефекта на корректность выполнения операций конечным пользователем | Severity |

#### 6.4.7 Критерии качества продукта
* Программный продукт должен работать в соответствии со спецификациями и требованиями (паспорт продукта);
* Функциональность должна полностью покрывать все требования, изложенные в руководствах пользователей (для Web, Mobile и Back-office);
* Программный продукт не должен иметь известных дефектов со статусом «Критический» и «Высокий» к моменту поставки программного продукта заказчику;
* Нефункциональные требования: SLA 99.9%, время ответа API < 200 мс, поддержка до 10 000 пользователей.

#### 6.4.8 Правила наименования пользователей системы CQ
Наименования пользователей в трекер-системе (CQ/Jira) происходит по следующей схеме: краткое имя = 1-ая буква имени + 2-е первые буквы фамилии. Например, для пользователя Natallia Hustyr, краткое имя в системе будет обозначено как NHU.

#### 6.4.9 Правила ведения переписки
В процессе проведения тестирования возникает необходимость ведения переписки с командой разработчиков. Со стороны заказчика контактными лицами, как правило, являются менеджер проекта для решения проектных вопросов, системный аналитик для решения вопросов связанных с корректностью функционирования системы, лидер команды разработчиков для обеспечения решения вопросов, связанных с отслеживанием дефектов. Со стороны группы тестирования проектные вопросы обращаются к лидеру команды тестирования / менеджеру проекта со стороны исполнителя, вопросы, связанные с дефектами, решаются или с лидером группы тестирования, или непосредственно с тестировщиком, зарегистрировавшим данный дефект.
Структура письма обязательно должна включать в себя «Заголовок», однозначно определяющий тему письма и тело письма, содержащее непосредственно запрос. В копию письма включаются все заинтересованные лица по данному вопросу.
Ответ на письмо обязательно должен быть отправлен не позднее четырех часов с момента получения письма. В случаях, когда нет возможности составить корректный ответ на поставленные в письме вопросы, получатель письма должен выслать нотификацию о получении письма и предположительную дату, когда будет выслан развернутый ответ на запрос. В случае, если ответ на письмо не получен в указанные сроки, письмо дублируется, в копию ставится менеджер проекта, который будет осуществлять контроль за исполнительностью подчиненного.

Документ описывает процесс тестирования, стратегию и подходы к проверке BookSphere — масштабируемой e-commerce платформы для продажи печатных книг, электронных книг и аудиокниг, построенной по архитектуре Headless Commerce.

Документ определяет взаимодействие группы тестирования и команды разработчиков, объем тестирования, тестовую конфигурацию, методологию, управление дефектами, график, риски и отчетность.

## 2.2 Цель документа

- Спланировать управление тестированием и техническую поддержку тестирования BookSphere на протяжении жизненного цикла разработки.
- Обеспечить полноту проверок в соответствии с требованиями к продукту, включая функциональные, интеграционные, нефункциональные и security-проверки.
- Организовать контроль процесса тестирования, определить методы регистрации дефектов, необходимое ПО и виды отчетности.
- Определить график работ, методологию, стратегию тестирования и критерии качества.
- Определить ресурсы, необходимые для реализации тестирования.
- Описать тестовую документацию, необходимую для обеспечения тестирования по проекту.

## 2.3 Целевая аудитория

Документ предназначен для сотрудников группы тестирования BookSphere, команды разработчиков, DevOps, ИБ, продуктовой команды и представителей заказчика. Он используется для понимания целей, содержания и порядка работ по тестированию, а также для согласования процессов регистрации и отслеживания дефектов.

## 2.4 Ссылки на проектную документацию

План тестирования основан на следующих проектных документах:

1. `BookSphere_Project_Plan.mpp` — план временных затрат, сроки и даты поставки промежуточных результатов.

4. `BookSphere_Technical_Testing.doc` — сценарии технического тестирования.
5. `BookSphere_Test_Log.xlsx` — журнал тестирования.
6. `BookSphere_Test_Scenarios.xlsx` — сценарии и тест-кейсы.
7. `BookSphere_API_Specification.yaml` — спецификация API и интеграционных контрактов.

## 2.5 Обзор программного продукта

BookSphere — масштабируемая e-commerce платформа нового поколения для продажи печатных книг, электронных книг и аудиокниг. Продукт построен по архитектуре Headless Commerce и поддерживает каналы Web, Mobile App, Smart TV и голосовые ассистенты.

Платформа включает клиентскую витрину, оформление заказа, административную панель, DRM-сервер, Headless CMS, AI-рекомендации, подписочную модель, маркетплейс, B2B-лицензии и уникальные функции: книжные клубы, AR-витрину, эко-трекинг и гибридный ридер с Immersion Reading.

Архитектура микросервисная, контейнеризованная: Next.js, Flutter, Python/FastAPI, Node.js/NestJS, Go/Gin, Keycloak, PostgreSQL, Redis, MongoDB, S3, Elasticsearch, Kubernetes, CI/CD, Prometheus/Grafana/ELK/Sentry.

## 2.6 Цели тестирования

Основными целями тестирования являются:

- Выявление проблем, связанных с несоответствием BookSphere требованиям.
- Отслеживание статуса проблем и контроль исправления дефектов.
- Предоставление суммарной оценки качества продукта.
- Снижение рисков проекта, связанных с качеством, безопасностью, интеграциями и нагрузкой.
- Подтверждение готовности кандидат-релиза к приемке заказчиком.

# 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основным методом проверки BookSphere является ручное функциональное тестирование методом «черного ящика» на основе требований и спецификаций. Дополнительно применяются автоматизированное, интеграционное, техническое и security-тестирование.

## 5.1 Функциональное тестирование

Функциональное тестирование проверяет соответствие BookSphere требованиям и правильность реализации функций. Выполняется вручную функциональным тестировщиком и включает два этапа.

### 5.1.1 Минимальный приемочный тест (Smoke Test)

МПТ — короткий тест не более 1 часа, проверяющий основную работоспособность BookSphere: вход/регистрацию, поиск и каталог, карточку товара, добавление в корзину, гостевой checkout в sandbox, тестовую оплату, создание заказа, просмотр статуса, вход в back-office, публикацию контентной страницы, выдачу DRM-лицензии на тестовый фрагмент.

По результатам МПТ принимается решение о допуске версии к дальнейшему тестированию. МПТ выполняется для каждой поставленной версии.

### 5.1.2 Регрессионное тестирование

Регрессионное тестирование обеспечивает проверку ранее протестированной функциональности после изменений, исправления дефектов и добавления новой функциональности. Включает повторное прохождение тест-кейсов, проверку исправленных дефектов, контроль отсутствия новых дефектов и совместимости модулей.

### 5.1.3 Функциональный тест

Функциональный тест — основной вид тестирования. Проверяются стандартные и нестандартные сценарии: граничные значения, специальные символы, большие объемы данных, бизнес-процессы, логические цепочки действий пользователей, взаимодействие функций, корректность обновления и отображения данных, завершение операций.

Особое внимание уделяется: checkout и платежам, подписке, маркетплейсу, B2B-лицензиям, DRM, синхронизации «Моей библиотеки», AI-рекомендациям, книжным клубам, AR-витрине, эко-трекингу, Immersion Reading, каналам Smart TV и голосовым ассистентам.

## 5.2 Автоматизированное тестирование

## 6.4 Управление дефектами

Средством регистрации и отслеживания дефектов является CQ (ClearQuest). Доступ предоставляется локально и через Web. CQ обеспечивает контроль статусов, историю, нотификации и отчетность по качеству.

### 6.4.1 Определение степени важности дефектов

Важность дефекта (Severity) определяет степень влияния на корректность работы конечного пользователя.

- **Критический (Critical)** — блокирует большую часть функциональности, полностью нерабочая функция или ветвь функциональности, либо приводит к потере информации.
- **Серьезный (Major)** — приводит к некорректной работе части функциональности, недоступности опций отдельной функции, но не блокирует тестирование в целом; может быть блокирующим для отдельной функции.
- **Средний (Average)** — неправильно работает неосновная часть функциональности, но есть альтернативный доступ к функциям и опциям.
- **Незначительный (Minor)** — приложение функционирует, бизнес-логика не нарушена, исправление может быть отложено.

### 6.4.2 Определение приоритета дефектов

Приоритет определяет срочность исправления дефекта и основывается на серьезности дефекта и критичности функции для пользователя.

- **Исправить незамедлительно (Resolve immediately)** — наивысший приоритет, исправление в кратчайшие сроки.
- **Уделить повышенное внимание (Give high attention)** — срочность ниже максимальной, но исправление требуется непосредственно.
- **Обычный (Normal queue)** — приоритет по умолчанию при регистрации.
- **Низкий (Low priority)** — исправление после устранения других ошибок.
- **Улучшение (Enhancement)** — предложение тестовой группы по улучшению интерфейса или качества; внедряется после валидации заказчиком.

### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

- При регистрации дефект получает статус **Submitted**, owner — лидер группы тестирования.
- Лидер группы тестирования проверяет воспроизведение и открывает дефект на лидера команды разработчиков — статус **Opened**.
- Лидер команды разработчиков квалифицирует дефект и назначает ответственного разработчика через **Modify**; меняется только поле Owner, статус остается **Opened**. CQ автоматически уведомляет разработчика.
- После исправления разработчик указывает версию сборки с фиксом, выполняет **Resolve**, owner — тестировщик, зарегистрировавший дефект; статус **Resolved**.
- Тестировщик проверяет исправление. Если корректно — **Validate**, статус **Closed**. Если нет — **Reject**, статус **Opened**, указываются причины и версия сборки, где дефект проверялся.
- На промежуточных этапах доступно **Modify** без изменения статуса, с сохранением комментариев.
- Лидер команды разработчиков может закрывать дефект через **Close** с резолюцией.
- Исправление может быть отложено через **Postpone** — статус **Postponed**.
- Если дефект уже зарегистрирован, ему присваивается **Duplicate** с указанием номера дубликата.
- Лидеры команд имеют право на **Delete**, но удаление не рекомендуется, так как история дефекта утрачивается.
- Если дефект не воспроизводится или описан недостаточно подробно, owner устанавливается тестировщик, зарегистрировавший дефект; тестировщик дополняет описание и уведомляет разработчика.

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основным методом проверки BookSphere будет ручное функциональное тестирование с использованием метода «черного ящика», которое базируется на требованиях и спецификациях и не предполагает специальных знаний о внутренней структуре объекта испытаний. Дополнительно применяются автоматизированное, техническое, нагрузочное и тестирование безопасности.

### 5.1 Функциональное тестирование

Функциональное тестирование — процесс тестирования программного продукта на предмет соответствия требованиям и правильности реализации всех характеристик, заложенных в продукт. Осуществляется вручную функциональным тестировщиком. Включает два этапа.

#### 5.1.1 Минимальный приемочный тест (Smoke Test)

МПТ — короткий тест, проверяющий основную функциональность BookSphere и ее работоспособность, длящийся не более 1 часа. По результатам МПТ принимается решение о допуске версии к дальнейшему тестированию.

Если очередная версия не прошла МПТ, по его результатам может быть принято решение о дальнейшем частичном тестировании либо о возврате версии на сборку/патч с исправлением критических дефектов. МПТ выполняется для каждой поставленной версии продукта. Основная задача — оперативное отслеживание регрессии качества и получение высокоуровневой картины работоспособности продукта.

#### 5.1.2 Регрессионное тестирование

Для обеспечения надлежащего качества на каждом последующем этапе производится регрессионное тестирование функциональности, разработанной на предыдущей стадии, и ее совместимости с новой функциональностью. Регрессионное тестирование подразумевает повторное прохождение тестовых случаев, проверку исправления дефектов, отсутствие непредвиденного влияния новых изменений, корректное взаимодействие и совместимость функций.

#### 5.1.3 Функциональный тест

Функциональный тест — основной вид теста, во время которого проверяется основная функциональность BookSphere при стандартном использовании, а также нестандартное использование, границы данных, ввод специальных символов и т.п. Используется весь объем созданной тестовой документации. Особое внимание уделяется бизнес-процессам, логическим цепочкам действий пользователей, взаимодействию функций, корректному обновлению и отображению данных, логическому завершению операций.

Основная цель функционального тестирования — обеспечить максимально возможное покрытие тестами программного продукта.

### 5.2 Автоматизированное тестирование

Автоматизированное тестирование входит в объем работ по проекту BookSphere и выполняется инженером автоматизации. Основная цель — решение сложных задач, выполнение которых не может быть осуществлено вручную в рамках сжатых сроков при минимальном привлечении ресурсов, а также обеспечение регулярной регрессии в CI/CD.

Автоматизированное тестирование подразумевает использование специального программного обеспечения для проведения автоматизированных тестов на основе набора тестовых данных и написанных скриптов. Применяются Playwright для Web, Appium/Flutter integration tests для Mobile, pytest для API, k6/JMeter/Gatling для нагрузки. Автотесты запускаются в GitLab CI/GitHub Actions, результаты публикуются в Jira и отчетах CI.

### 5.3 Техническое тестирование

Техническое тестирование имеет основной целью проверку нефункциональных требований BookSphere и выполняется техническим тестировщиком с использованием k6, JMeter, Gatling, Prometheus, Grafana, ELK Stack и Sentry. Включает нагрузочное тестирование, тест производительности, тестирование больших объемов данных, стресс-тесты, измерение временных параметров и восстановление после сбоев.

Параметры нагрузочного тестирования:

| Параметр | Значение |
|---|---|
| Профиль нагрузки | Ramp-up 10 минут до 10 000 одновременных пользователей; плато 60 минут; спад 10 минут. Общая длительность сценария — 80 минут. |
| Стресс-профиль | Дополнительный прогон до 15 000 пользователей для проверки деградации и восстановления; восстановление не более 10 минут. |
| Распределение операций | 30% — каталог/поиск; 20% — карточка товара и Look Inside; 15% — корзина/checkout; 10% — аутентификация/личный кабинет; 8% — оплата в sandbox; 7% — «Моя библиотека»/аудиоплеер; 5% — отзывы/модерация; 5% — рекомендации, голосовой канал и Smart TV. |
| Критерии p95 | Чтение каталога/поиска/карточки: p95 ≤ 200 мс; checkout: p95 ≤ 500 мс; внешние платежные вызовы: p95 ≤ 2 000 мс. |
| Критерии p99 | Чтение каталога/поиска/карточки: p99 ≤ 500 мс; checkout: p99 ≤ 1 000 мс; внешние платежные вызовы: p99 ≤ 5 000 мс. |
| Допустимый процент ошибок | Общий уровень ошибок ≤ 0,5%; для критических сценариев оплаты, заказа и авторизации ≤ 0,1%; доля HTTP 5xx ≤ 0,1%. |
| Доступность | SLA 99,9%; не более 8 часов простоя в год на плановые работы. |
| Масштабируемость | Проверка auto-scaling микросервисов при росте нагрузки; отсутствие потери заказов и платежных событий. |

Подробное описание этапов проведения технического тестирования приведено в документе [4].

## 6 МЕТОДОЛОГИЯ ТЕСТИРОВАНИЯ

### 6.1 Обзор процесса

Подход к процессу тестирования отображен на схеме:

```mermaid
flowchart TD
    A["1. Получение требований к программному продукту"] --> B["2. Анализ требований, определение целей и задач тестирования"]
    B --> C["3. Разработка проектной документации: план, тест-кейсы, сценарии, наборы данных"]
    C --> D["4. Установка очередной версии продукта на тестовую платформу"]
    D --> E["5. Проведение МПТ"]
    E -->|"Не пройден"| F["Отказ МПТ: сборка/патч с исправлением критических дефектов"]
    F --> D
    E -->|"Пройден"| G["6. Регрессионное тестирование и валидация исправленных дефектов"]
    G --> H["7. Полный цикл функциональных тестов; регистрация дефектов"]
    H --> I["8. Тестирование технической документации"]
    I --> J["9. Отчет заказчику о качестве и перечне дефектов"]
    J --> K["10. Исправление дефектов командой разработки/заказчиком"]
    K --> L["11. Сборка новой версии продукта"]
    L --> M["12. Нотификация об изменениях; анализ новой функциональности"]
    M --> N["13. Внесение изменений в тестовую документацию"]
    N --> O["14. Повторный цикл тестирования"]
    O -->|"Не кандидат-релиз"| D
    O -->|"Кандидат-релиз"| P["15. Полное приемо-сдаточное тестирование"]```


Процесс включает следующие этапы:

1. Получение требований к программному продукту (предоставляется заказчиком).
2. Анализ требований, определение целей и постановка задач по тестированию (определяется в данном документе).
3. Разработка проектной документации:
   - план тестирования: определение тестовой стратегии; выявление ресурсов; определение тестовой конфигурации; расчет трудоемкости; составление предварительного графика;
   - написание Test Cases для функциональных тестов, разработка тестовых сценариев и наборов тестовых данных для технического и автоматизированного тестирования.
4. Установка очередной версии продукта на тестовую платформу.
5. Проведение МПТ и принятие решения о приемке версии для тестирования или отказе. В случае отказа ожидается сборка очередной версии с исправленными критическими дефектами.
6. Регрессионное тестирование — проверка и валидация исправленных дефектов, проверка отсутствия новых дефектов.
7. Проведение полного цикла функциональных тестов; регистрация дефектов.
8. Проведение тестирования технической документации (руководства пользователей).
9. Предоставление отчета заказчику о качестве программного продукта с перечнем выявленных дефектов.
10. Исправление дефектов командой разработчиков/заказчиком.
11. Сборка новой версии программного продукта.
12. Получение группой тестирования нотификации об изменениях в новой версии, анализ новой функциональности.
13. Внесение изменений в тестовую документацию в связи с новой функциональностью или изменением требований.
14. Повторный цикл тестирования (возврат к этапу 4).
15. При выпуске кандидат-релиза — выполнение полного приемо-сдаточного тестирования.

#### 6.3.1 Процесс доставки

Новые версии продукта выкладываются заказчиком в согласованное хранилище артефактов (GitLab/GitHub Releases, S3-совместимое хранилище или FTP по требованию заказчика). Каждая новая версия сопровождается e-mail нотификацией на проектную команду с указанием:

#### 6.3.2 Критерии приемки на тестирование

Тестирование новой версии может быть отложено полностью или частично в следующих случаях:

- в новой версии не было внесено никаких изменений;
- программный продукт содержит ошибки, которые не позволяют провести тестирование большей части функциональности (блокированы ветви функциональности);
- новая версия недоступна для тестирования.

### 6.4 Управление дефектами

Средством регистрации и отслеживания текущего состояния дефектов для проекта BookSphere выбрана Jira. Выбор обусловлен необходимостью постоянного контроля заинтересованными сторонами за появлением новых дефектов, возможностью своевременного управления статусами, гибкой настройкой workflow, ролевым доступом, интеграцией с CI/CD и Git, dashboards, JQL-запросами и уведомлениями. Jira предоставляется через Web; при требовании 152-ФЗ возможен контур Jira Data Center на стороне заказчика.

В Jira настроены статусы, совпадающие с состояниями стандарта: Submitted, Opened, Resolved, Closed, Duplicate, Postponed. Действия стандарта сопоставлены с переходами Jira.

| Состояние стандарта | Статус Jira | Действия Jira |
|---|---|---|
| Submitted | Submitted | Submit (создание), Open, Close, Duplicate |
| Opened | Opened | Open, Modify, Resolve, Close, Postpone, Duplicate, Reject, Re-open |
| Resolved | Resolved | Resolve, Validate, Reject |
| Closed | Closed | Close, Validate, Re-open |
| Duplicate | Duplicate | Duplicate, Close |
| Postponed | Postponed | Postpone, Open, Close |

#### 6.4.1 Определение степени важности дефектов

Важность дефекта (Severity) требуется для правильной оценки степени влияния дефекта на корректность выполнения операций конечным пользователем. Используются единые термины: Критический, Серьезный, Средний, Незначительный.

| Важность | Описание |
|---|---|
| Критический (Critical) | Дефект, блокирующий большую часть функциональности, полностью нерабочая функция, ветвь функциональности или дефект, приводящий к потере информации. |
| Серьезный (Major) | Дефект, приводящий к некорректной работе части функциональности, недоступности опций отдельной функции, но не блокирующий тестирование в целом; либо блокирующая ошибка отдельной функции, не влияющая на работу всей системы. |
| Средний (Average) | Ошибка в неправильно работающей неосновной части функциональности, не препятствующая тестированию; присутствуют методы альтернативного доступа к функциям и опциям. |
| Незначительный (Minor) | Приложение может успешно функционировать, бизнес-логика не нарушена, исправление дефекта откладывается на последнюю очередь. |

#### 6.4.2 Определение приоритета дефектов

Приоритет дефекта определяется, чтобы правильно оценить, насколько срочно требуется исправление. Приоритет основан на серьезности дефекта и критичности функции для пользователя.

| Приоритет | Описание |
|---|---|
| Исправить незамедлительно (Resolve immediately) | Исправление имеет наивысший приоритет, выполняется в первую очередь в кратчайшие сроки. |
| Уделить повышенное внимание (Give high attention) | Нет необходимости в сверхсрочном исправлении, но устранение ошибки должно быть осуществлено непосредственно. |
| Обычный (Normal queue) | Дефолтный приоритет при регистрации дефектов. |
| Низкий (Low priority) | Дефекты исправляются только после устранения всех других ошибок. |
| Улучшение (Enhancement) | Предложения тестовой группы по улучшению качества интерфейса; внедряются только после валидации заказчиком. |

В качестве резолюции о причине закрытия дефекта из состояний Submitted, Opened, Postponed, Duplicate могут рассматриваться:

- разработано согласно требованиям (дефект открыт ошибочно);
- дефект несущественный и не требует исправления (не нарушены бизнес-требования);
- коррекция дефекта нецелесообразна — исправление окажет критическое действие на большую часть функциональности (предложение по изменению требований к продукту).

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

- При регистрации дефект приобретает статус Submitted (регистрируется тестировщиками); owner дефекта — лидер группы тестирования.
- Лидер группы тестирования проверяет воспроизведение дефекта и открывает его на лидера команды разработчиков (дефект приобретает статус Opened).
- Лидер команды разработчиков квалифицирует дефект и назначает ответственного за исправление разработчика (action = Modify); редактируется поле Owner, как правило, это разработчик функции. Дефект остается в состоянии Opened. В Jira автоматически формируется и отправляется нотификация ответственному лицу.
- Разработчик после исправления дефекта проставляет версию билда, в котором будет доступен фикс, выбирает action = Resolve, назначает owner = тестировщик, осуществивший регистрацию, дефект переходит в состояние Resolved.
- Тестировщик проверяет исправление. Если дефект исправлен корректно — action = Validate, дефект переходит в Closed. Если дефект не исправлен или исправлен частично — action = Reject, указывается версия билда, в котором дефект тестировался, описываются проблемы и owner = разработчик; дефект снова переходит в Opened. Цикл повторяется.
- На всех промежуточных этапах дефект можно редактировать (action = Modify); это не изменяет статус, но сохраняет изменения и комментарии.
- Лидер команды разработчиков может закрывать дефект (action = Close) с выставлением резолюций, если дефект не обнаружен, разработано согласно требованиям или исправление невозможно — делается запрос на изменение требований.
- Исправление дефекта по разным причинам может быть отложено — action = Postpone (state = Postponed).
- Если подобный дефект уже был зарегистрирован, ему присваивается статус Duplicate с указанием номера дублирующего дефекта. Дублирование допускается из Submitted и из Opened.
- Если дефект не воспроизводится у разработчиков, недостаточно подробно описан процесс воспроизведения или не ясен смысл ошибки, лидер команды разработчиков или разработчик выставляет Owner = тестировщик, осуществивший регистрацию, и пишет письмо/комментарий в Jira с перечнем конкретных вопросов. Тестировщик дополняет дефект в Jira комментариями, выставляет Owner = лицо, запросившее дополнительную информацию, и нотифицирует разработчика.

| Важность | Время реакции | Время назначения ответственного | Целевое время исправления | Время валидации | Комментарий |
|---|---|---|---|---|---|
| Критический | 15 минут | 30 минут | 4 часа / hotfix | 2 часа | Останавливает ключевые сценарии; эскалация лидеру тестирования и PM |
| Серьезный | 1 час | 2 часа | 1 рабочий день | 4 часа | Блокирует отдельную функцию; исправление в ближайшем билде |
| Средний | 4 часа | 1 рабочий день | 5 рабочих дней | 1 рабочий день | Допускается workaround; включается в текущий спринт |
| Незначительный | 1 рабочий день | 3 рабочих дня | 15 рабочих дней или следующий релиз | 1 рабочий день | Исправляется после более важных дефектов |

#### 6.4.8 Правила наименования пользователей системы Jira

Наименование пользователей в Jira происходит по следующей схеме: краткое имя = 1-я буква имени + 2-е первые буквы фамилии. Например, для пользователя Natallia Hustyr краткое имя в системе будет обозначено как NHU.

#### 6.4.9 Правила ведения переписки

В процессе тестирования возникает необходимость ведения переписки с командой разработчиков. Со стороны заказчика контактными лицами, как правило, являются менеджер проекта для решения проектных вопросов, системный аналитик для вопросов корректности функционирования системы, лидер команды разработчиков для вопросов отслеживания дефектов, зарегистрированных в Jira. Со стороны группы тестирования проектные вопросы адресуются лидеру команды тестирования / менеджеру проекта со стороны исполнителя; вопросы, связанные с дефектами, решаются с лидером группы тестирования или непосредственно с тестировщиком, зарегистрировавшим дефект.

Структура письма обязательно должна включать «Заголовок», однозначно определяющий тему письма, и тело письма с непосредственно запросом. В копию включаются все заинтересованные лица по данному вопросу. Ответ на письмо должен быть отправлен не позднее четырех часов с момента получения. Если нет возможности составить корректный ответ, получатель высылает нотификацию о получении письма и предполагаемую дату развернутого ответа. Если ответ не получен в указанные сроки, письмо дублируется, в копию ставится менеджер проекта для контроля исполнительности. Комментарии по дефектам также фиксируются в Jira.

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основной метод — ручное функциональное тестирование «чёрным ящиком» на основе требований и спецификаций, supplemented автоматизированным и техническим тестированием.

### 5.1 Функциональное тестирование

Функциональное тестирование проверяет соответствие BookSphere требованиям и корректность реализации функций. Выполняется функциональным тестировщиком.

#### 5.1.1 Минимальный приёмочный тест (Smoke Test)

МПТ — короткий тест основной функциональности, длительностью не более 1 часа. По результатам принимается решение о допуске версии к дальнейшему тестированию. МПТ выполняется для каждой поставленной версии. При отказе версия возвращается на исправление критических дефектов.

#### 5.1.2 Регрессионное тестирование

Регрессионное тестирование проверяет исправление дефектов, отсутствие новых дефектов и совместимость новой функциональности с ранее протестированной. Выполняется повторное прохождение тестовых случаев после завершения предыдущего этапа.

#### 5.1.3 Функциональный тест

Функциональный тест проверяет основную и нестандартную функциональность: граничные значения, специальные символы, бизнес-процессы, логические цепочки, взаимодействие функций, обновление и отображение данных, завершение операций. Используется весь объём тестовой документации.

### 5.2 Автоматизированное тестирование

Автоматизация входит в объём тестирования BookSphere. Автоматизируются регрессионные, интеграционные, API- и smoke-проверки, а также подготовка тестовых данных. Автоматизация выполняется техническим тестировщиком совместно с функциональной командой. Результаты автоматизации включаются в журнал и отчётность.

### 5.3 Техническое тестирование

Техническое тестирование проверяет нефункциональные требования: нагрузку, производительность, устойчивость, восстановление, большие объёмы данных и узкие места.

| Параметр | Значение |
|---|---|
| Профиль нагрузки | Ramp-up 15 мин → плато 60 мин → спад 15 мин; всего 90 мин |
| Пиковая нагрузка | До 10 000 одновременных пользователей |
| Распределение операций | Каталог/поиск — 35%; карточка товара — 20%; корзина/checkout — 15%; авторизация/личный кабинет/библиотека — 10%; AI-рекомендации — 10%; отзывы/модерация — 5%; back-office/API — 5% |
| Требование task.md | Время ответа API < 200 мс |
| Допущение: p95 внутреннего API | < 200 мс |
| Допущение: p99 внутреннего API | < 500 мс |
| Допущение: p95 checkout | < 2 с |
| Допущение: p95 внешних платежей | < 3 с |
| Допущение: допустимый процент ошибок | ≤ 1% всех запросов; ≤ 0,1% для критических операций |

Отдельно фиксируется: требование «API < 200 мс» взято из task.md; пороги checkout и внешних платежей являются допущением.

### 6.3 Доставка новых версий программного продукта

#### 6.3.1 Процесс доставки

Новые версии размещаются заказчиком на FTP-сервере или передаются иным согласованным способом. Каждая версия сопровождается e-mail-нотификацией с номером версии и перечнем изменений. К началу повторного цикла разработчики приводят дефекты в Jira в актуальное состояние: исправленные дефекты переводятся на валидацию, владельцами становятся тестировщики, зарегистрировавшие дефекты.

#### 6.3.2 Критерии приёмки на тестирование

Тестирование версии может быть отложено полностью или частично, если:

- в версии нет изменений;
- дефекты блокируют большую часть функциональности;
- версия недоступна для тестирования.

### 6.4 Управление дефектами

Для регистрации и отслеживания дефектов используется Jira. Выбор обоснован необходимостью прозрачного контроля статусов, истории изменений, разграничения ролей, интеграции с CI/CD и отчётности. Jira обеспечивает доступ заинтересованных сторон и снижает необходимость отдельных отчётов. Все упоминания прежнего трекера заменены на Jira.

#### 6.4.1 Определение степени важности дефектов

Важность дефекта (Severity) нужна для оценки влияния на корректность работы BookSphere.

| Важность | Описание |
|---|---|
| Критический | Блокирует большую часть функциональности, полностью нерабочая функция или ветвь, приводит к потере информации. |
| Серьёзный | Приводит к некорректной работе части функциональности, недоступности опций, блокирует отдельную функцию, но не всю систему. |
| Средний | Неправильно работает неосновная часть функциональности, есть обходной путь, тестирование не блокируется. |
| Незначительный | Приложение работает, бизнес-логика не нарушена, исправление откладывается на последнюю очередь. |

**Допущение: SLA реакции и исправления по важности**

| Важность | Время реакции | Время исправления |
|---|---:|---:|
| Критический | 15 минут | 8 часов |
| Серьёзный | 1 час | 2 рабочих дня |
| Средний | 4 часа | 5 рабочих дней |
| Незначительный | 8 часов | следующий релиз |

#### 6.4.2 Определение приоритета дефектов

Приоритет определяется на основе серьёзности дефекта и критичности функции для пользователя.

- «Исправить незамедлительно» — наивысший приоритет, исправление в кратчайшие сроки.
- «Уделить повышенное внимание» — срочное исправление не требуется, но устранение необходимо в ближайшее время.
- «Обычный» — приоритет по умолчанию при регистрации.
- «Низкий» — исправление после всех других ошибок.
- «Улучшение» — предложение тестовой группы, внедряется после валидации заказчиком.

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

При регистрации дефект получает статус Submitted, owner — руководитель группы тестирования. Руководитель группы тестирования проверяет воспроизведение и открывает дефект на лидера команды разработчиков — статус Opened. Лидер команды разработчиков квалифицирует дефект и выполняет Modify: редактируется только поле Owner, как правило, назначается разработчик функции; статус остаётся Opened. Jira автоматически уведомляет разработчика функции.

После исправления разработчик функции указывает версию сборки с фиксом, выполняет Resolve, owner = тестировщик, осуществивший регистрацию; дефект переходит в Resolved. Тестировщик проверяет исправление: при успехе выполняет Validate → Closed; при неуспехе — Reject → Opened, owner = разработчик функции, указываются причины и версия проверки. Цикл повторяется.

На промежуточных этапах доступен Modify — изменение полей и комментариев без смены статуса. Лидер команды разработчиков может закрывать дефект через Close с резолюцией. Исправление может быть отложено через Postpone → Postponed. Если дефект дублирует ранее зарегистрированный, используется Duplicate из Submitted или Opened с указанием номера дублирующего дефекта. Если дефект не воспроизводится или описан недостаточно подробно, owner переводится на тестировщика, который дополняет описание в Jira и уведомляет разработчика.

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основной метод — ручное функциональное тестирование «чёрным ящиком» на основе требований и спецификаций, дополняется автоматизированным и техническим тестированием.

### 5.1 Функциональное тестирование

Функциональное тестирование проверяет соответствие BookSphere требованиям и корректность реализации функций. Выполняется функциональным тестировщиком.

#### 5.1.1 Минимальный приёмочный тест (Smoke Test)

МПТ — короткий тест основной функциональности, длительностью не более 1 часа. По результатам принимается решение о допуске версии к дальнейшему тестированию. МПТ выполняется для каждой поставленной версии. При отказе версия возвращается на исправление критических дефектов.

#### 5.1.2 Регрессионное тестирование

Регрессионное тестирование проверяет исправление дефектов, отсутствие новых дефектов и совместимость новой функциональности с ранее протестированной. Выполняется повторное прохождение тестовых случаев после завершения предыдущего этапа.

#### 5.1.3 Функциональный тест

Функциональный тест проверяет основную и нестандартную функциональность: граничные значения, специальные символы, бизнес-процессы, логические цепочки, взаимодействие функций, обновление и отображение данных, завершение операций. Используется весь объём тестовой документации.

### 5.2 Автоматизированное тестирование

Автоматизация входит в объём тестирования BookSphere. Автоматизируются регрессионные, интеграционные, API- и smoke-проверки, а также подготовка тестовых данных. Автоматизация выполняется техническим тестировщиком совместно с функциональной командой. Результаты автоматизации включаются в журнал и отчётность.

### 5.3 Техническое тестирование

Техническое тестирование проверяет нефункциональные требования: нагрузку, производительность, устойчивость, восстановление, большие объёмы данных, узкие места, безопасность и соответствие.

| Параметр | Значение |
|---|---|
| Профиль нагрузки | Ramp-up 15 мин → плато 60 мин → спад 15 мин; всего 90 мин |
| Пиковая нагрузка | До 10 000 одновременных пользователей |
| Распределение операций | Каталог/поиск — 35%; карточка товара — 20%; корзина/checkout — 15%; авторизация/личный кабинет/библиотека — 10%; AI-рекомендации — 10%; отзывы/модерация — 5%; back-office/API — 5% |
| Требование task.md | Время ответа API < 200 мс |
| Допущение: p95 внутреннего API | < 200 мс |
| Допущение: p99 внутреннего API | < 500 мс |
| Допущение: p95 checkout | < 2 с |
| Допущение: p95 внешних платежей | < 3 с |

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

При регистрации дефект получает статус Submitted, owner — руководитель группы тестирования. Руководитель группы тестирования проверяет воспроизведение и открывает дефект на лидера команды разработчиков — статус Opened. Лидер команды разработчиков квалифицирует дефект и выполняет Modify: редактируется только поле Owner, как правило, назначается разработчик функции; статус остаётся Opened. Jira автоматически уведомляет разработчика функции.

После исправления разработчик функции указывает версию сборки с фиксом, выполняет Resolve, owner = тестировщик, осуществивший регистрацию; дефект переходит в Resolved. Тестировщик проверяет исправление: при успехе выполняет Validate → Closed; при неуспехе — Reject → Opened, owner = разработчик функции, указываются причины и версия проверки. Цикл повторяется.

На промежуточных этапах доступен Modify — изменение полей и комментариев без смены статуса. Лидер команды разработчиков может закрывать дефект через Close с резолюцией; при закрытии из Opened ответственным лицом становится руководитель группы тестирования. Исправление может быть отложено через Postpone → Postponed. Если дефект дублирует ранее зарегистрированный, используется Duplicate из Submitted или Opened с указанием номера дублирующего дефекта. Если дефект не воспроизводится или описан недостаточно подробно, owner переводится на тестировщика, который дополняет описание в Jira и уведомляет разработчика.

Лидеры команд имеют право на удаление дефектов из системы (action = Delete) — не рекомендуется, так как информация по дефекту и его история полностью утрачиваются.

Контактные лица со стороны заказчика: менеджер проекта — по проектным вопросам, системный аналитик — по функционированию системы, лидер команды разработчиков — по дефектам. Со стороны группы тестирования: руководитель группы тестирования — по проектным вопросам, тестировщик, зарегистрировавший дефект, — по дефектам.

Письмо должно содержать «Заголовок», однозначно определяющий тему, и тело с запросом. В копию включаются заинтересованные лица. Ответ направляется не позднее 4 часов с момента получения. Если корректный ответ невозможен, отправитель уведомляет о получении и указывает предполагаемую дату развёрнутого ответа. При отсутствии ответа письмо дублируется с копией менеджера проекта.
