## 5. СТРАТЕГИЯ ТЕСТИРОВАНИЯ
### 5.1 Функциональное тестирование
* **Smoke Test (МПТ)**: Проверка критического пути (Поиск -> Добавление в корзину -> Оплата -> Доступ к электронной книге) после каждого деплоя в CI/CD.
* **Regression Test**: Автоматизированный регресс API и критических UI-путей перед каждым релизом.
* **Functional / E2E Test**: Проверка бизнес-процессов:
  * *B2C*: Покупка бумажной книги с расчетом доставки (СДЭК), оформление подписки, использование промокодов.
  * *B2B*: Выдача корпоративных лицензий, массовое добавление пользователей.
  * *Оффлайн-режим*: Синхронизация прогресса чтения Flutter-приложения при потере/восстановлении сети.

### 5.2 Автоматизированное тестирование
* **API Testing**: Покрытие 100% эндпоинтов микросервисов (FastAPI, NestJS, Go). Контрактное тестирование интеграций.
* **UI Testing**: Автотесты на Playwright (Web) и Appium (Mobile) для основных сценариев (Авторизация, Поиск, Checkout).

### 5.3 Техническое (Нефункциональное) тестирование
* **Нагрузочное (Performance)**: Имитация 10 000 одновременных пользователей (пиковые распродажи). Контроль метрики: время ответа API < 200 мс.
* **Безопасность (Security)**: Аудит на SQL-инъекции, XSS, DDoS-устойчивость. Проверка соответствия 152-ФЗ (маскирование ПДн) и PCI DSS (токенизация карт).
* **Тестирование DRM**: Попытки дампинга, обхода шифрования электронных и аудиокниг, проверки лимитов устройств.
* **Тестирование AI**: Валидация логики коллаборативной фильтрации (корректность выдачи рекомендаций «Для вас»).

## 6. МЕТОДОЛОГИЯ ТЕСТИРОВАНИЯ
### 6.1 Обзор процесса (Agile / Scrum)
Тестирование встроено в CI/CD (GitLab CI). 
1. Анализ требований и API-контрактов.
2. Написание тест-кейсов и автотестов.

5. Подписание релиза.

### 6.2 Тестовая документация
* **Test Management**: Jira / Zephyr (или YouTrack).
* **Тест-кесы и Чек-листы**: Хранятся в репозитории проекта (Markdown/Allure).
* **Баг-репорты**: Заводятся в Jira с обязательным приложением логов (ELK) и трассировки (Jaeger).

### 6.4 Управление дефектами
**Степени важности (Severity):**
* **Critical**: Падение микросервиса, потеря данных, невозможность оплаты, обход DRM.
* **Major**: Не работает фильтрация, не синхронизируется прогресс чтения, ошибка в BI-дашбордах.
* **Minor**: UI-баги, опечатки, незначительные задержки анимаций (Framer Motion).

**Жизненный цикл дефекта:**
`New` -> `Open` (Подтвержден QA Lead) -> `In Progress` (Разработчик) -> `Resolved` (Готов к ретесту) -> `Closed` (Подтверждено QA) / `Reopened` (Ошибка не исправлена).

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основным методом проверки данного программного продукта будет ручное функциональное тестирование с использованием метода «чёрного ящика», который базируется на использовании требований и спецификаций и не предполагает наличия каких-либо специальных знаний о конфигурации и внутренней структуре объекта испытаний.

В процессе тестирования BookSphere будут применяться следующие его типы:

### 5.1 Функциональное тестирование

Функциональное тестирование – это процесс тестирования программного продукта на предмет соответствия требованиям к программному продукту и правильности реализации всех характеристик, заложенных в продукт. Осуществляется вручную функциональным тестировщиком. Данный вид тестирования будет включать в себя два этапа:

#### 5.1.1 Минимальный приёмочный тест (Smoke Test)

МПТ – это короткий тест, проверяющий основную функциональность программного продукта и его работоспособность, длящийся не более 1 часа. По результатам приёмочного теста принимается решение о допуске версии программного продукта к дальнейшему тестированию.

Если очередная версия программного продукта не прошла приёмочный тест, то по его результатам может быть принято решение о дальнейшем частичном тестировании программного продукта. Минимальный приёмочный тест будет выполняться для каждой из поставленных версий продукта. Основная его задача – это оперативное отслеживание регрессии качества и получение высокоуровневой картины работоспособности продукта.

#### 5.1.2 Регрессионное тестирование

Для обеспечения надлежащего качества продукта на каждом последующем этапе будет производиться регрессионное тестирование функциональности, разработанной на предыдущей стадии, и её совместимости с новой функциональностью. Регрессионное тестирование подразумевает под собой повторное прохождение всех тестовых случаев, протестированных после завершения предыдущего этапа разработки системы, проверки исправления дефектов, допущенных на этом этапе разработки системы, непоявления новых, корректного взаимодействия и совместимости функций.

#### 5.1.3 Функциональный тест

Функциональный тест – основной вид теста, во время которого проверяются основная функциональность программного продукта при стандартном его использовании, а также проверяется нестандартное использование программного продукта, границы переполнения массивов данных, ввод специальных символов и т. п. Для проведения функционального теста используется весь объём созданной тестовой документации. Особое внимание уделяется тестированию бизнес-процессов системы (полный цикл оформления заказа, подписка, работа маркетплейса, B2B-лицензии), логических цепочек последовательностей действий пользователей, взаимодействию функций системы между собой, корректному обновлению и отображению данных, логическому завершению операций.

Основная цель функционального тестирования – обеспечить максимально возможное покрытие тестами программного продукта.

### 5.2 Автоматизированное тестирование

Основной целью автоматизации тестирования является решение сложных задач, выполнение которых не может быть осуществлено вручную в рамках сжатых сроков при минимальном привлечении ресурсов.

Автоматизированное тестирование подразумевает под собой использование специального программного обеспечения для проведения автоматизированных тестов на основе набора тестовых данных и написанных скриптов. Осуществляется разработчиком автоматизированных тестов.

Допущение: для автоматизации UI-тестов используется Playwright, для API-тестов – Postman/Newman в связке с GitLab CI. Данный вид тестирования будет осуществляться и планироваться по дополнительному соглашению с заказчиком.

### 5.3 Техническое тестирование

Техническое тестирование имеет своей основной целью проверку нефункциональных требований, предъявляемых к программному продукту, и будет осуществляться с использованием прикладного программного обеспечения k6 и производиться техническим тестировщиком.

Данный вид тестирования включает в себя несколько типов тестов:

- Нагрузочное тестирование – проверка работоспособности системы при одновременной работе до 10 000 пользователей;
- Тест производительности – проверка быстродействия работы системы, времени отклика API (целевой показатель < 200 мс) при вызове различных функций;
- Тестирование работоспособности системы при больших объёмах данных (проверка функционирования системы при работе с крупной базой данных каталога);
- Стресс-тесты – проверка работоспособности системы в критических условиях (пиковые нагрузки во время распродаж, исчерпание ресурсов узлов Kubernetes);
- Измерение временных параметров работы системы;
- Восстановление работоспособности системы при сбоях (проверка auto-scaling микросервисов, отказоустойчивость кластера Kubernetes);
- Тестирование безопасности: проверка соответствия PCI DSS, 152-ФЗ / GDPR, защита от DDoS и SQL-инъекций, целостность DRM-защиты электронных книг.

Подробное описание этапов проведения технического тестирования приведено в документе [4].

### 6.3 Доставка новых версий программного продукта

#### 6.3.1 Процесс доставки

Новые версии продукта собираются посредством пайплайна GitLab CI и разворачиваются на тестовом кластере Kubernetes в Yandex Cloud. Артефакты сборки (Docker-образы микросервисов) публикуются в контейнерном реестре.

Каждая новая версия должна сопровождаться нотификацией на проектную команду (электронная почта и/или сообщение в рабочем мессенджере) с указанием:

- номера версии продукта;
- произведённых изменений;
- перечня исправленных дефектов (со ссылками на задачи в Jira).

К моменту начала проведения повторного цикла тестирования разработчики должны привести состояния дефектов в дефект-трекинговой системе в актуальное состояние (исправленные дефекты должны быть отправлены на валидацию, исполнителями дефектов должны стать тестировщики, осуществившие регистрацию дефектов).

#### 6.3.2 Критерии приёмки на тестирование

Тестирование новой версии программного продукта может быть отложено полностью или частично в одном из следующих случаев:

- В новой версии программного продукта не было внесено никаких изменений;
- Программный продукт содержит ошибки, которые не позволяют провести тестирование большей части функциональности (блокированы ветви функциональности);
- Новая версия программного продукта не доступна для тестирования (сборка не развёрнута на тестовом кластере Kubernetes или пайплайн GitLab CI завершился с ошибкой);
- Отсутствует нотификация с описанием изменений и перечнем исправленных дефектов.

### 6.4 Управление дефектами

Средством регистрации и отслеживания текущего состояния дефектов для данного проекта выбран инструмент Jira. Выбор данного прикладного программного обеспечения обусловлен необходимостью постоянного контроля заинтересованными сторонами появления новых дефектов, возможностью своевременного управления статусами дефектов, дистанционным доступом и отсутствием необходимости составления дополнительных отчётов, содержащих информацию о качестве тестируемого программного продукта.

Данный продукт будет развёрнут в облачной версии (Jira Cloud), и заказчику будет предоставлен доступ через веб-интерфейс.

#### 6.4.1 Определение степени важности дефектов

Важность дефекта (Severity) требуется для правильной оценки степени влияния дефекта на корректность выполнения операций конечным пользователем.

Различают следующие степени важности дефектов:

- **«Критический» (Critical)** – дефект, блокирующий большую часть функциональности, полностью нерабочая функция, ветвь функциональности или дефект, приводящий к потере информации (например, потеря данных заказов, утечка персональных данных пользователей, неработоспособность платёжного шлюза).
- **«Серьёзный» (Major)** – дефект, приводящий к некорректной работе части функциональности, недоступности опций отдельной функции, но не блокирующий тестирование в целом. Также это может быть блокирующая ошибка для отдельной функции, не оказывающей влияния на работу всей системы или ветви её функционала (например, некорректный расчёт стоимости доставки, ошибка синхронизации прогресса чтения в «Моей библиотеке»).
- **«Средний» (Average)** – ошибка характеризуется неправильно работающей неосновной части функциональности, не препятствующая проведению тестирования (т. е. присутствуют методы альтернативного доступа к функциям и их опциям) (например, некорректное отображение рекомендаций, ошибки в блоке отзывов при наличии альтернативного способа просмотра).
- **«Незначительный» (Minor)** – приложение может успешно функционировать, не нарушена бизнес-логика, исправление дефекта откладывается на последнюю очередь (например, опечатки в интерфейсе, незначительные визуальные дефекты).

#### 6.4.2 Определение приоритета дефектов

Приоритет дефекта определяется, чтобы правильно оценить, насколько срочно требуется исправление дефекта.

Приоритет должен быть основан на:
- Серьёзности дефекта.
- Критичности функции для пользователя.

Различают следующие приоритеты:

- **«Исправить незамедлительно» (Highest)** – исправление дефекта имеет наивысший приоритет, должно быть осуществлено в первую очередь в кратчайшие сроки.
- **«Уделить повышенное внимание» (High)** – нет необходимости в сверхсрочном исправлении дефекта, но устранение ошибки должно быть осуществлено непосредственно.
- **«Обычный» (Medium)** – дефолтный приоритет при регистрации дефектов.
- **«Низкий» (Low)** – дефекты исправляются только после устранения всех других ошибок в программе.
- **«Улучшение» (Enhancement)** – предложения тестовой группы по улучшению качества интерфейса (внедряется только после валидации заказчиком).

Схематично цикл жизни дефекта можно описать с помощью следующей диаграммы (Рис. 2):

Рис. 2

Жизненный цикл дефекта включает следующие состояния:

1. **Зарегистрирован (To Do)** – дефект создан тестировщиком.
2. **Открыт (In Progress)** – дефект подтверждён и передан команде разработчиков.
3. **В работе (In Progress)** – назначен ответственный разработчик.
4. **Исправлен (Done)** – разработчик исправил дефект и указал версию сборки.

9. **Дублирован (Duplicate)** – дефект дублирует ранее зарегистрированный.
10. **Повторно открыт (Reopened)** – дефект проявился повторно после закрытия.

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки ПО при работе с дефект-трекинговой системой

При регистрации дефекта он приобретает статус To Do (регистрируется тестировщиками) – выставляется исполнитель (Assignee) дефекта – лидер команды тестирования.

Лидер команды тестирования проверяет воспроизведение дефекта и открывает его на лидера команды разработчиков (дефект приобретает статус In Progress).

Лидер команды разработчиков квалифицирует дефект и назначает ответственного за его исправление разработчика (действие = Assign), редактируется значение только поля Assignee, как правило это разработчик функции (дефект остаётся в состоянии In Progress). В системе автоматически формируется и отсылается нотификация ответственному лицу – разработчику функции о том, что он назначен ответственным за исправление данного дефекта.

Разработчик после исправления дефекта проставляет версию сборки, в которой будет доступен фикс для тестирования (поле Fix Version), переводит дефект в статус Done; исполнителем назначается тестировщик, осуществивший регистрацию дефекта.

Тестировщик проверяет исправление дефекта. В случае если дефект исправлен корректно, тестировщик переводит дефект в статус Closed. Если дефект не исправлен или исправлен частично, тестировщик выполняет действие Reopen (указывает в комментарии номер версии сборки, в которой дефект был оттестирован, описывает проблемы, почему дефект не исправлен), исполнителем назначается разработчик, осуществлявший исправление, дефект снова переходит в состояние In Progress. В этом случае разработчик снова осуществляет исправление и переводит дефект в состояние Done с указанием новой версии приложения, в которой будет доступен фикс. Цикл повторяется.

Из состояния Closed дефект может быть снова открыт (применяется действие Reopen) в случае его повторного проявления.

На всех промежуточных этапах дефект можно редактировать, это действие не изменяет статуса дефекта, но сохраняет изменения и комментарии.

Лидер команды разработчиков может закрывать дефект (действие = Close) с выставлением резолюций (в случаях если дефект не обнаружен, разработано согласно требованиям, исправление дефекта невозможно – делается запрос на изменение требований заказчикам).

Исправление дефекта по разным причинам может быть отложено – действие = Move to Backlog (состояние = Backlog).

В случае если подобный дефект уже был зарегистрирован, ему присваивается статус Duplicate с указанием номера дефекта, которого он дублирует.

Лидеры команд имеют право на удаление дефектов из системы (не рекомендуется, информация по дефекту и его история полностью утрачивается).

В случае если дефект не воспроизводится у разработчиков, недостаточно подробно описан процесс воспроизведения дефекта или не ясен общий смысл ошибки, лидер команды разработчиков (или разработчик, занимающийся исправлением дефекта) назначает исполнителем тестировщика, осуществившего регистрацию дефекта, и пишет комментарий/письмо тестировщику с перечнем конкретных вопросов, что именно непонятно в зарегистрированном дефекте.

Тестировщик дополняет дефект в Jira необходимыми комментариями, назначает исполнителем лицо, запросившее дополнительную информацию, и нотифицирует этого разработчика о том, что недостатки описания дефекта устранены.

#### 6.4.7 Критерии качества продукта

- Программный продукт должен работать в соответствии со спецификациями и требованиями;
- Функциональность должна полностью покрывать все требования, изложенные в руководствах пользователей (в случае разбиения развития программного продукта на итерации должна быть полностью реализована функциональность, запланированная на итерацию);
- Программный продукт не должен иметь известных дефектов со статусом «Критический» и «Серьёзный» к моменту поставки программного продукта заказчику;
- Время ответа API не должно превышать 200 мс при нагрузке до 10 000 одновременных пользователей;
- Доступность системы (SLA) должна составлять не менее 99,9 %;
- Система должна соответствовать требованиям PCI DSS, 152-ФЗ / GDPR по защите персональных данных и платёжной информации;
- DRM-защита электронных книг должна предотвращать нелегальное копирование.

#### 6.4.8 Правила наименования пользователей системы Jira

Наименование пользователей в Jira происходит по следующей схеме: краткое имя = 1-я буква имени + 2 первые буквы фамилии. Например, для пользователя Natallia Hustyr краткое имя в системе будет обозначено как NHU.

Допущение: при наличии однофамильцев к краткому имени добавляется порядковый номер (например, NHU1, NHU2).

#### 6.4.9 Правила ведения переписки

В процессе проведения тестирования возникает необходимость ведения переписки с командой разработчиков. Со стороны заказчика контактными лицами, как правило, являются менеджер проекта для решения проектных вопросов, системный аналитик для решения вопросов, связанных с корректностью функционирования системы, лидер команды разработчиков для обеспечения решения вопросов, связанных с отслеживанием дефектов, зарегистрированных в системе; со стороны группы тестирования проектные вопросы адресуются лидеру команды тестирования / менеджеру проекта со стороны исполнителя, вопросы, связанные с дефектами, решаются или с лидером группы тестирования, или непосредственно с тестировщиком, зарегистрировавшим данный дефект.

Структура письма обязательно должна включать в себя «Заголовок», однозначно определяющий тему письма, и тело письма, содержащее непосредственно запрос. В копию письма включаются все заинтересованные лица по данному вопросу.

Ответ на письмо обязательно должен быть отправлен не позднее четырёх часов с момента получения письма. В случаях когда нет возможности составить корректный ответ на поставленные в письме вопросы, получатель письма должен выслать нотификацию о получении письма и предположительную дату, когда будет выслан развёрнутый ответ на запрос. В случае если ответ на письмо не получен в указанные сроки, письмо дублируется, в копию ставится менеджер проекта, который будет осуществлять контроль за исполнительностью подчинённого.

## 5 СТРАТЕГИЯ ТЕСТИРОВАНИЯ

Основным методом проверки BookSphere является функциональное тестирование методом «чёрного ящика» на основе требований Описания продукта, дополненное автоматизированным тестированием в CI/CD и техническим тестированием нефункциональных требований.

### 5.1 Функциональное тестирование

Функциональное тестирование — процесс проверки соответствия программного продукта требованиям Описания продукта и правильности реализации всех заявленных характеристик. Осуществляется функциональными тестировщиками вручную и с использованием автоматизированных скриптов.

#### 5.1.1 Минимальный приёмочный тест (Smoke Test)

Smoke Test — автоматизированный прогон, проверяющий основную функциональность платформы, длительностью **не более 30 минут** (A2). По результатам принимается решение о допуске сборки к дальнейшему тестированию. Запускается в GitLab CI на каждый merge request и на каждую сборку, развёртываемую в тестовом окружении.

Перечень проверок Smoke Test для BookSphere:

| № | Проверка | Сервис / Компонент | Ожидаемый результат |
|---|---|---|---|
| 1 | Поиск «Толстой» в каталоге возвращает релевантные результаты | Каталог и Поиск (FastAPI + Elasticsearch) | HTTP 200, в выдаче ≥ 3 позиций, время ответа < 200 мс |
| 2 | Карточка товара «Война и мир» загружается с тремя форматами (бумага, PDF, MP3) и фрагментом Look Inside | Web-клиент (Next.js) + Каталог | Все секции отображаются, фрагмент открывается |
| 3 | Авторизация пользователя через Keycloak, получение JWT-токена | Пользователи и Аутентификация (Go + Keycloak) | HTTP 200, токен выдан, роль корректна |
| 4 | Добавление книги в корзину, пересчёт суммы | Корзина и Заказы (NestJS) + Redis | HTTP 201, сумма корректна, корзина сохранена в Redis |
| 5 | Гостевой checkout: оформление заказа без регистрации | Корзина и Заказы (NestJS) | HTTP 201, заказ создан со статусом «Новый» |
| 6 | Применение промокода «BOOK10» пересчитывает итоговую сумму | Корзина и Заказы (NestJS) | Сумма уменьшена на 10 %, промокод отмечен как применённый |
| 7 | Платёжный запрос в sandbox ЮKassa завершается успешно | Платёжные интеграции | Статус платежа «succeeded», заказ переходит в «Оплачен» |
| 8 | Личный кабинет: история заказов отображает созданный заказ | Пользователи + Корзина и Заказы | Заказ виден в списке, статус корректен |
| 9 | «Моя библиотека»: приобретённый e-book открывается во встроенном ридере | Mobile-клиент (Flutter) + DRM-сервер | Файл расшифрован, ридер отображает текст |
| 10 | Лента AI-рекомендаций «Для вас» возвращает ≥ 5 позиций | AI и Рекомендации (PyTorch) | HTTP 200, массив содержит ≥ 5 элементов |
| 11 | Админ-панель: создание карточки товара в Headless CMS сохраняется и отображается в каталоге | Headless CMS (Strapi) + Каталог | HTTP 201, товар появляется в поиске в течение 60 секунд |
| 12 | Уведомление о новом заказе отправляется через SendGrid (sandbox) | Уведомления | Письмо зафиксировано в логе SendGrid, содержит номер заказа |

Если сборка не проходит Smoke Test, она возвращается команде разработки; дальнейшее тестирование блокируется.

#### 5.1.2 Регрессионное тестирование

На каждом спринте (2 недели) и при получении новой сборки выполняется регрессионное тестирование: повторное прохождение автоматизированных и ручных тест-кейсов, покрывающих функциональность предыдущих спринтов, проверка исправления зарегистрированных дефектов и отсутствия новых. Регрессионный набор автоматизирован на ≥ 80 % и запускается в GitLab CI (цель 2.6, п. 6).

#### 5.1.3 Функциональный тест

Функциональный тест — основной вид тестирования, в ходе которого проверяется:

- Основная функциональность при стандартном использовании (полные бизнес-сценарии: поиск → карточка → корзина → оплата → доставка → библиотека).
- Нестандартное использование: границы переполнения полей, ввод специальных символов в поиск, одновременное редактирование карточки товара двумя контент-менеджерами.
- Взаимодействие микросервисов: согласованность данных между каталогом (FastAPI), корзиной (NestJS), складом (1С/МойСклад) и уведомлениями.
- Корректность обновления и отображения данных в реальном времени (статусы доставки, трекинг).
- Логическое завершение операций: полный цикл жизни заказа от «Новый» до «Доставлен» / «Возврат».
- Подписочная модель, маркетплейс, B2B-лицензии.
- Оффлайн-режим мобильного приложения: работа без сети, синхронизация при восстановлении соединения (A6).

### 5.2 Автоматизированное тестирование

Автоматизация является обязательной частью плана и встроена в CI/CD (GitLab CI). Цель — обеспечить быструю обратную связь и снизить стоимость регрессии.

| Тип автотестов | Инструмент | Область покрытия | Запуск |
|---|---|---|---|
| API-тесты микросервисов | PyTest (Python) для FastAPI; Newman / Jest для NestJS; Go test для Gin | Все эндпоинты каталога, корзины, пользователей, заказов | Каждый merge request, ночной прогон |
| Контрактные тесты внешних API | Pact + Pact Broker | ЮKassa, CloudPayments, Stripe, СДЭК, Почта России, 1С, МойСклад, Bitrix24, SendGrid, Литрес, Storytel (A3) | Каждый merge request при изменении интеграционного слоя |
| UI-тесты Web (Next.js) | Playwright (Chromium, Firefox, WebKit) | Каталог, карточка товара, корзина, checkout, личный кабинет, админ-панель | Ночной прогон, перед релизом |
| UI-тесты Mobile (Flutter) | Appium + Flutter Driver | Аудиоплеер, оффлайн-режим, ридер, синхронизация | Перед релизом, на реальных устройствах (A6) |
| Нагрузочные скрипты | k6 (Grafana Cloud) | Сценарии: каталог, поиск, checkout, подписка | Еженедельно, перед релизом (раздел 5.3) |
| Интеграционные тесты с моками | WireMock + Testcontainers | Взаимодействие микросервисов в K8s, работа с PostgreSQL, Redis, MongoDB, S3 | Каждый merge request |

Все автотесты хранятся в репозитории проекта, запускаются в Docker-контейнерах на GitLab Runner (A10). Результаты публикуются в GitLab CI/CD как артефакты; падение блокирует merge.

### 5.3 Техническое тестирование

Техническое тестирование проверяет нефункциональные требования из Описания продукта. Осуществляется инженером по нагрузочному тестированию с использованием k6, Prometheus, Grafana и инструментов Kubernetes.

**Типы технического тестирования:**

| Тип | Описание | Критерий |
|---|---|---|
| Нагрузочное тестирование | Моделирование до 10 000 одновременных пользователей (показатель из Описания продукта); сценарии: поиск, просмотр карточки, добавление в корзину, checkout, чтение в библиотеке | Время ответа API < 200 мс (из Описания продукта); ошибки < 0,1 % (рекомендуемый порог: при 10 000 VU допустимо не более 10 ошибок на 10 000 запросов для обеспечения SLA 99.9 %) |
| Тест производительности | Измерение времени отклика отдельных эндпоинтов: поиск в Elasticsearch, создание заказа, выдача DRM-лицензии | 95-й перцентиль < 200 мс; 99-й перцентиль < 500 мс (рекомендуемый порог: 99-й перцентиль допускается выше среднего, но не должен превышать 500 мс, чтобы не деградировать пользовательский опыт) |
| Стресс-тестирование | Нагрузка сверх целевой (15 000 VU) для определения точки отказа; проверка поведения auto-scaling в K8s | Система деградирует плавно, не теряет данные; auto-scaling увеличивает число подов в течение ≤ 120 секунд (рекомендуемый порог: обусловлен типичным временем холодного старта контейнера в K8s) |
| Тестирование больших объёмов данных | Работа с базой: 1 000 000 записей каталога, 500 000 пользователей, 2 000 000 заказов (A9) | Поиск и фильтрация не деградируют; пагинация работает корректно |
| Тестирование восстановления и отказоустойчивости (failover) | Остановка подов, переключение реплик PostgreSQL, сбой узла K8s, разрыв связи с внешним сервисом | Восстановление в течение ≤ 60 секунд (рекомендуемый порог: обеспечивает вклад в SLA 99.9 %); данные не теряются |

### 6.3 Доставка новых версий программного продукта

#### 6.3.1 Процесс доставки

Новая сборка развёртывается командой разработки в тестовом окружении Kubernetes через CI/CD-пайплайн (GitLab CI). После развёртывания формируется автоматическая нотификация в командный канал (Telegram / email) с указанием:

- номера сборки (тег контейнера / Git SHA);
- перечня изменений (merge requests, вошедшие в сборку);
- перечня дефектов, переведённых в статус «Исправлен» в Jira.

К моменту начала регрессионного тестирования разработчики обязаны актуализировать статусы дефектов в Jira: исправленные дефекты переведены в «Ready for QA», владельцем назначен тестировщик, зарегистрировавший дефект.

#### 6.3.2 Критерии приёмки на тестирование

Тестирование новой сборки может быть отложено полностью или частично, если:

- В сборке отсутствуют изменения относительно предыдущей протестированной версии.
- Сборка содержит дефекты со степенью «Критический», блокирующие более 50 % функциональности (например, недоступен сервис аутентификации Keycloak или не разворачивается микросервис каталога).
- Сборка не развёрнута в тестовом окружении или развёрнута с ошибками (падение подов, CrashLoopBackOff в K8s).

- Разработано согласно требованиям (дефект зарегистрирован ошибочно).
- Дефект не существенный и не требует исправления (бизнес-требования не нарушены).
- Коррекция нецелесообразна: исправление окажет критическое воздействие на большую часть функциональности (формируется запрос на изменение требований).

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки при работе с дефект-трекинговой системой

1. При регистрации дефект получает статус **Зарегистрирован** (Jira: Backlog); владелец — QA Lead.
2. QA Lead проверяет воспроизведение дефекта и переводит его в **Открыт** (Jira: In Progress), назначая ответственным лидера команды разработчиков.
3. Лидер команды разработчиков квалифицирует дефект и назначает ответственного разработчика (действие «Изменить»); в Jira обновляется поле Assignee. Система автоматически отправляет нотификацию назначенному разработчику.
4. Разработчик после исправления указывает сборку (тег контейнера / Git SHA), в которой доступен фикс, переводит дефект в **Исправлен** (Jira: Ready for QA) и назначает владельцем тестировщика, зарегистрировавшего дефект.
5. Тестировщик проверяет исправление. Если дефект исправлен — переводит в **Закрыт** (Jira: Closed). Если нет — выполняет **Отказ в валидации**: указывает номер сборки, описывает проблему, возвращает в **Открыт** (Jira: In Progress) с назначением разработчика. Цикл повторяется.
6. Из состояния **Закрыт** дефект может быть повторно открыт (Re-open) при повторном проявлении.
7. На любом этапе допустимо редактирование комментар

## 5. Стратегия тестирования

Основным методом проверки является функциональное тестирование методом «чёрного ящика», базирующееся на требованиях описания продукта. Автоматизация тестирования является обязательной частью процесса и интегрирована в CI/CD-пайплайн (GitLab CI) с целевым покрытием не менее 80 % тестовых сценариев.

### 5.1 Функциональное тестирование

Функциональное тестирование — проверка соответствия платформы требованиям описания продукта и корректности реализации всех характеристик. Включает три этапа:

#### 5.1.1 Минимальный приёмочный тест (Smoke Test)

Автоматизированный Smoke Test выполняется при каждой сборке release-candidate в CI/CD-пайплайне. Длительность — не более **30 минут**. Все внешние сервисы заменены моками (A2). Результат: пройден / не пройден. При непрохождении сборка не допускается к дальнейшему тестированию, пайплайн блокируется.

**Состав проверок Smoke Test (12 проверок):**

| № | Проверка | Сервис / компонент | Критерий прохождения |
|---|---|---|---|
| 1 | Health-check всех микросервисов | API Gateway → FastAPI, NestJS, Go Gin, PyTorch-сервис, Strapi, DRM | HTTP 200 на /health каждого сервиса за ≤ 5 с |
| 2 | Регистрация и авторизация пользователя | Keycloak (Go Gin) | Токен доступа выдан; роль присвоена корректно |
| 3 | Поисковый запрос возвращает результаты | FastAPI + Elasticsearch | Запрос «фантастика» возвращает ≥ 1 результат за < 200 мс |
| 4 | Карточка товара загружается со всеми форматами | FastAPI (каталог) + S3 (MinIO) | Форматы «печать», «PDF», «MP3» отображаются; фрагмент Look Inside доступен |
| 5 | Добавление товара в корзину | NestJS | Товар в корзине; итоговая сумма пересчитана |
| 6 | Гостевой checkout с моком оплаты | NestJS + WireMock (ЮKassa) | Заказ создан; статус «Оплачен»; мок возвращает успешный ответ |
| 7 | Применение промокода | NestJS | Скидка применена; итоговая сумма уменьшена |
| 8 | Загрузка DRM-защищённого фрагмента | DRM-сервер + MinIO | Файл расшифрован для авторизованного пользователя; копирование заблокировано |
| 9 | Offline-режим: e-book доступен без сети | Flutter-приложение (эмулятор, сеть отключена) | Книга открывается; прогресс сохраняется локально |
| 10 | Отправка уведомления через мок | Сервис уведомлений + WireMock (SendGrid / Telegram) | Уведомление о создании заказа отправлено; мок получил запрос |
| 11 | Создание товара через Headless CMS | Strapi | Товар создан; отображается в каталоге после индексации |
| 12 | AI-рекомендации возвращают ответ | PyTorch-сервис | HTTP 200; JSON содержит ≥ 5 рекомендаций; время ответа < 200 мс |

#### 5.1.2 Регрессионное тестирование

Регрессионное тестирование выполняется при каждой новой сборке после исправления дефектов. Включает:
- Повторное прохождение автоматизированных тестовых сценариев, покрывающих функциональность предыдущих спринтов.
- Проверку исправления зарегистрированных дефектов (валидация).
- Подтверждение отсутствия новых ошибок в смежных модулях.
- Проверку корректного взаимодействия микросервисов после изменений.

Регрессионный набор запускается автоматически в GitLab CI при каждом merge в develop и при сборке release-candidate (A10).

#### 5.1.3 Функциональный тест

Основной вид тестирования, при котором проверяется:
- Основная функциональность при стандартном использовании.
- Нестандартное использование: границы переполнения, ввод специальных символов, конкурентные операции (одновременная покупка последнего экземпляра).
- Сквозные бизнес-процессы: полный цикл заказа (от поиска до доставки), цикл подписки, цикл маркетплейса, B2B-лицензирование.
- Логические цепочки последовательностей действий пользователей.
- Корректность обновления и отображения данных между сервисами (каталог ↔ корзина ↔ заказ ↔ склад ↔ уведомление).
- Дефолтные значения, валидация полей, защита от несанкционированного доступа.

Особое внимание уделяется тестированию бизнес-процессов: оформление заказа с несколькими форматами, применение бонусов лояльности, синхронизация прогресса чтения между Web и Mobile, работа маркетплейса с комиссией, автопродление подписки.

### 5.2 Автоматизированное тестирование

Автоматизация является обязательной частью процесса и входит в CI/CD-пайплайн. Целевое покрытие — не менее 80 % тестовых сценариев.

| Уровень | Инструмент | Язык / фреймворк | Область применения |
|---|---|---|---|
| API-тесты: Каталог и Поиск | pytest + httpx | Python | Микросервис на FastAPI |
| API-тесты: Корзина и Заказы | Jest + Supertest | JavaScript / TypeScript | Микросервис на NestJS |
| API-тесты: Пользователи и Аутентификация | go test -cover | Go | Микросервис на Go Gin |
| API-тесты: AI-рекомендации | pytest + httpx | Python | Микросервис на PyTorch |
| E2E Web | Playwright | TypeScript | Витрина на Next.js, административная панель |
| Мобильные тесты | Appium + flutter_test | Dart / Python | Flutter-приложение (iOS, Android) |
| Контрактное тестирование | Pact | Python / JS / Go | Взаимодействие между микросервисами |
| Нагрузочные тесты | k6 | JavaScript | Все публичные API-эндпоинты |

Автоматизированные тесты хранятся в репозитории проекта и запускаются:
- При каждом merge в develop (регрессионный набор).
- При сборке release-candidate (полный набор + Smoke).
- По расписанию: ночной прогон полного набора на функциональном стенде.

### 5.3 Техническое тестирование

Техническое тестирование проверяет нефункциональные требования к платформе. Включает:

**5.3.1 Нагрузочное тестирование**
- Проверка работоспособности при 10 000 одновременных пользователей (требование описания).
- Ступенчатое увеличение нагрузки: шаг 1 000 VU, длительность ступени 10 минут, общее время сессии не менее 72 часов для подтверждения SLA.
- Критерий: среднее время ответа < 200 мс для всех сервисов; p99 ≤ 500 мс (рекомендуемый); ноль ошибок 5xx при целевой нагрузке.

**5.3.2 Тест производительности**
- Время отклика при вызове ключевых функций (поиск, добавление в корзину, checkout, загрузка рекомендации).
- Пропускная способность (RPS) каждого микросервиса.

**5.3.3 Тестирование при больших объёмах данных**
- Каталог ≥ 50 000 SKU, база заказов ≥ 100 000 записей (A4).
- Проверка деградации времени поиска в Elasticsearch при росте индекса.

**5.3.4 Стресс-тесты**
- Нагрузка выше целевой (15 000 VU) до момента деградации.
- Определение точки отказа и поведения системы за пределом.

**5.3.5 Тестирование отказоустойчивости и восстановления**
- Переключение PostgreSQL (primary → replica); проверка отсутствия потери данных.
- Убий пода микросервиса (kill -9); проверка auto-scaling и восстановления за ≤ 60 с.
- Отказ узла Elasticsearch; проверка деградации поиска.

**5.3.6 Проверка SLA 99,9 %**
- Мониторинг доступности в течение нагрузочной сессии ≥ 72 часов (Prometheus + Grafana).
- Failover-тесты: плановое переключение узлов, обновление rolling-update без простоя.
- Расчёт: допустимое время простоя ≤ 8 часов в год; в рамках теста фиксируется суммарное время недоступности за сессию.

**5.3.7 Проверка auto-scaling**
- Имитация роста нагрузки; проверка срабатывания Horizontal Pod Autoscaler.
- Подтверждение масштабирования на резервный узел функционального стенда.

**5.3.8 Интеграционное тестирование**

Проверка взаимодействия между микросервисами платформы по сквозным сценариям (заказ → оплата → склад → доставка → уведомление → личный кабинет).

**5.3.9 Контрактное тестирование внешних API**

Контрактное тестирование (Pact) и проверка на моках выполняются по группам интеграций:

| Группа интеграций | Сервисы | Метод проверки |
|---|---|---|
| Платёжные шлюзы | ЮKassa, CloudPayments, Stripe | Контрактный тест (схема запроса/ответа) + мок успешного платежа, отказа, таймаута, возврата |
| Логистика | Shiptor, GotoRoute (агрегаторы для СДЭК, Почта России, Boxberry, Яндекс.Доставка) | Контрактный тест расчёта стоимости и трекинга + мок недоступности агрегатора |
| ERP и Склад | 1С:Предприятие, МойСклад | Контрактный тест двустороннего обмена остатками и ценами; проверка разрешения конфликтов |
| CRM | Bitrix24, amoCRM | Контрактный тест передачи лида и истории покупок |
| Коммуникации | SendGrid, Twilio / SMS.ru, Telegram Bot API | Мок-сервер; проверка формата сообщения, повторной отправки при ошибке |
| Поставщики контента | Литрес, Storytel | Контрактный тест получения метаданных и DRM-файлов; проверка обработки битого файла и таймаута |

**5.3.10 Тестирование безопасности**
- Сканирование контейнеров: Trivy (образы в GitLab Registry).
- DAST-сканирование API: OWASP ZAP (автоматический прогон в CI/CD).
- Проверка чек-листа PCI DSS для модуля приёма карт (предварительная проверка перед внешним аудитом) (A6).
- Проверка 152-ФЗ / GDPR: отсутствие персональных данных в логах, в ответах API без авторизации, в клиентском коде.
- Проверка ролевой модели: контент-менеджер не имеет доступа к заказам; оператор не изменяет каталог.
- Тестирование защиты от SQL-инъекций и XSS на всех формах ввода.

### 6.3 Доставка новых версий программного продукта

#### 6.3.1 Процесс доставки

Новые сборки размещаются в GitLab Registry (контейнерные образы) и развёртываются на функциональный стенд через GitLab CI/CD (A1, A3).

Каждая сборка сопровождается записью в канале проектной коммуникации с указанием:
- номера версии (тега) образа;
- перечня включённых изменений и номеров исправленных дефектов.

К моменту начала регрессионного тестирования разработчики актуализируют статусы дефектов в Jira: исправленные дефекты переведены в статус «Исправлен», ответственным назначен тестировщик, зарегистрировавший дефект.

#### 6.3.2 Критерии приёмки на тестирование

Тестирование новой сборки может быть отложено полностью или частично в следующих случаях:
- В сборке не содержится изменений относительно предыдущей версии.
- Сборка содержит дефекты, блокирующие прохождение Smoke Test (≥ 2 из 12 проверок не пройдены).
- Сборка не развёрнута на стенде или стенд недоступен.

### 6.4 Управление дефектами

Средством регистрации и отслеживания дефектов является **Jira** (с плагином Xray для привязки к тестовым сценариям). Выбор обусловлен возможностью интеграции с GitLab CI, гибкой настройкой воркфлоу, доступом для всех участников проекта и формированием отчётов без дополнительных инструментов.

#### 6.4.1 Определение степени важности дефектов

| Степень важности | Определение | Пример из BookSphere |
|---|---|---|
| Критический (Critical) | Блокирует основную функциональность; полная неработоспособность функции или ветви; потеря данных | Невозможно оформить заказ; пропадают данные корзины при перезапуске сервиса; утечка платёжных данных |
| Серьёзный (Major) | Некорректная работа части функциональности; недоступность опций; блокировка отдельной функции без влияния на всю платформу | Не применяется промокод; не синхронизируется прогресс чтения между устройствами; ошибка расчёта доставки |
| Средний (Average) | Неправильно работающая неосновная часть; есть альтернативный доступ | Не отображается инфографика сюжета в карточке товара; некорректная сортировка в каталоге; задержка отображения отзыва |
| Незначительный (Minor) | Платформа функционирует; бизнес-логика не нарушена | Орфографическая ошибка в тексте уведомления; незначительное смещение элемента в мобильном интерфейсе |

#### 6.4.2 Определение приоритета дефектов

Приоритет определяется на основе серьёзности дефекта и критичности функции для пользователя.

| Приоритет | Определение | Пример из BookSphere |
|---|---|---|
| Highest | Исправление в первую очередь, в кратчайшие сроки | Падение сервиса оплаты при нагрузке 10 000 VU |
| High | Устранение непосредственно в текущем спринте | Не работает поиск по автору в каталоге |
| Medium | Исправление в порядке очереди, в ближайшем спринте | Не отображаются видеообзоры на карточке товара в Safari |
| Low | Исправление после устранения всех остальных дефектов | Неидеальное выравнивание иконки в футере |

#### 6.4.3 Цикл жизни дефекта

```mermaid
stateDiagram-v2
    [*] --> Зарегистрирован : Регистрация дефекта
    Зарегистрирован --> Открыт : Открыть
    Зарегистрирован --> Закрыт : Закрыть (не подтверждён)
    Зарегистрирован --> Дублирован : Дублировать
    Открыт --> Исправлен : Исправить
    Открыт --> Отложен : Отложить
    Открыт --> Закрыт : Закрыть (не дефект)
    Исправлен --> Закрыт : Валидировать
    Исправлен --> Открыт : Отклонить (не исправлен)
    Отложен --> Открыт : Возобновить
    Отложен --> Закрыт : Закрыть
    Закрыт --> [*]
    Дублирован --> [*]
\```

Терминальные статусы (не имеют исходящих переходов): **Закрыт**, **Дублирован**.
Если закрытый дефект проявляется повторно, регистрируется новый дефект со ссылкой на исходный.

#### 6.4.4 Матрица переходов

| № | Предыдущее состояние | Действие | Новое состояние | Кто выполняет | Статус в Jira |
|---|---|---|---|---|---|
| 1 | — (нет) | Регистрация | Зарегистрирован | Тестировщик | To Do |
| 2 | Зарегистрирован | Открыть | Открыт | QA Lead | In Progress |
| 3 | Зарегистрирован | Закрыть | Закрыт | QA Lead | Done |
| 4 | Зарегистрирован | Дублировать | Дублирован | QA Lead | Duplicate |
| 5 | Открыт | Исправить | Исправлен | Разработчик функции | In Review |
| 6 | Открыт | Отложить | Отложен | Лидер разработки | Blocked |
| 7 | Открыт | Закрыть | Закрыт | Лидер разработки | Done |
| 8 | Исправлен | Валидировать | Закрыт | Тестировщик | Done |
| 9 | Исправлен | Отклонить | Открыт | Тестировщик | In Progress |
| 10 | Отложен | Возобновить | Открыт | Лидер разработки | In Progress |
| 11 | Отложен | Закрыть | Закрыт | Лидер разработки | Done |

Каждый нетерминальный статус (Зарегистрирован, Открыт, Исправлен, Отложен) имеет не менее одного исходящего перехода.

Резолюции при закрытии из состояний «Зарегистрирован», «Открыт», «Отложен»:
- Разработано согласно требованиям (дефект не подтверждён).
- Дефект не влияет на бизнес-логику и не требует исправления.
- Исправление нецелесообразно: требуется изменение требований (запрос к заказчику).

#### 6.4.5 Процесс взаимодействия команд тестирования и разработки при работе с дефект-трекинговой системой

1. Тестировщик регистрирует дефект в Jira (статус To Do). Ответственный — QA Lead.
2. QA Lead проверяет воспроизведение и переводит дефект в In Progress, назначая лидера разработки.
3. Лидер разработки квалифицирует дефект и назначает ответственного разработчика. Разработчик получает уведомление из Jira.
4. Разработчик исправляет дефект, указывает версию сборки с фиксом, переводит в In Review. Ответственным становится тестировщик, зарегистрировавший дефект.
5. Тестировщик валидирует исправление:
   - Исправлено → переводит в Done.
   - Не исправлено → отклоняет (возврат в In Progress), указывает причину и номер сборки, в которой проверял. Цикл повторяется.
6. Если дефект не воспроизводится у разработчика, разработчик возвращает дефект тестировщику с запросом дополнительной информации. Тестировщик дополняет описание и возвращает разработчику.

#### 6.4.6 Регистрация дефектов

Обязательные поля при регистрации дефекта в Jira:

| Поле | Описание |
|---|---|
| ID | Идентификационный номер (присваивается автоматически) |
| Заголовок | Краткое описание с привязкой к функции (например: «Корзина: сумма не пересчитывается при применении промокода») |
| Степень важности | Критический / Серьёзный / Средний / Незначительный |
| Приоритет | Highest / High / Medium / Low |
| Модуль / Компонент | Микросервис или клиентское приложение (Каталог, Корзина, Пользователи, AI, Web, Mobile, CMS, DRM, Уведомления) |
| Группа функций | Подмодуль (Поиск, Checkout, Подписка, Маркетплейс и т. д.) |
| Версия сборки | Номер тега контейнерного образа |
| Компонент исправления | Заполняется разработчиком: сервис, в котором будет доступен фикс |
| Описание | Полное описание, шаги воспроизведения, фактический и ожидаемый результат |
| Окружение | Стенд (функциональный / нагрузочный), браузер / устройство |
| Прикреплённые файлы | Скриншоты, логи, видео, дампы запросов |
| Связь с тест-кейсом | Ссылка на сценарий в Xray (при наличии) |

#### 6.4.7 Критерии качества продукта

- Платформа работает в соответствии с функциональными и нефункциональными требованиями описания продукта.
- Функциональность полностью покрывает требования, запланированные на текущий этап (спринт).
- Среднее время ответа каждого микросервиса < 200 мс при нагрузке 10 000 VU.
- SLA 99,9 % подтверждено мониторингом и failover-тестами.
- К моменту поставки отсутствуют дефекты со степенью важности «Критический» и «Серьёзный» в любом статусе, кроме «Закрыт» (включая «Отложен» и «Исправлен, не проверен»).
- Покрытие автоматизированными тестами ≥ 80 % тестовых сценариев.
- Ноль открытых уязвимостей Critical / High по результатам OWASP ZAP и Trivy.

Пример: пользователь **Иван Петров** → имя в системе **
