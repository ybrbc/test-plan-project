## 2. Introduction

### 2.1. Назначение
Настоящий план определяет стратегию, объём, ресурсы, критерии и процедуры тестирования платформы **BookSphere** — headless e-commerce платформы для продажи печатных, электронных и аудиокниг (B2C, B2B, внутренние пользователи). План охватывает как MVP (Релиз 1.0), так и Full-версию (Релиз 2.0).

### 2.2. Исполнительное резюме
Тестирование должно подтвердить, что BookSphere:
- обеспечивает корректный пользовательский путь от поиска книги до оплаты и доставки/доступа к цифровому контенту;
- соответствует нефункциональным требованиям (API < 200 мс, 10 000 одновременных пользователей, SLA 99.9%);
- соответствует требованиям безопасности и комплаенса (PCI DSS, 152-ФЗ/GDPR, DRM);
- корректно интегрируется с внешними системами (платёжные шлюзы, логистика, 1С/МойСклад, CRM, коммуникации, поставщики контента).

### 2.3. Ссылки
- Паспорт программного продукта «BookSphere» (task.md)
- IEEE 829-1998 Test Plan Template
- Требования к безопасности: PCI DSS, 152-ФЗ, GDPR
- API-спецификации микросервисов (OpenAPI/Swagger)
- Документация интеграций: ЮKassa, CloudPayments, Stripe, СДЭК, Почта России, Boxberry, Яндекс.Доставка, 1С, МойСклад, Bitrix24/amoCRM, SendGrid, Twilio/SMS.ru, Telegram Bot API, Литрес/Storytel

### 2.4. Объём
**В объёме:** клиентская витрина (Web Next.js, Mobile Flutter), checkout, back-office, API Gateway, микросервисы (каталог/поиск, корзина/заказы, пользователи/аутентификация, AI-рекомендации), интеграции, DRM, инфраструктура (K8s, мониторинг), нефункциональные требования.

**Вне объёма:** внутренняя реализация сторонних сервисов (провайдеры оплаты, логистики, издательства) — тестируются только точки интеграции и обработка ответов/ошибок.

### 2.5. Управление изменениями
Изменения объёма/подхода согласуются через Change Control Board (QA Lead, Tech Lead, Product Owner). Каждое изменение фиксируется в истории ревизий.

## 6. Approach

### 6.1. Общая стратегия
Многоуровневая стратегия: **unit → integration → system → acceptance**, с параллельным нефункциональным тестированием (performance, security, usability, compatibility). Приоритет — критический путь покупки (поиск → карточка → корзина → checkout → оплата → доставка/доступ к контенту).

### 6.2. Уровни и распределение

| Уровень | Что тестируется | Ответственность |
|---|---|---|
| Unit | Модули микросервисов | Разработчики |
| Integration | API Gateway ↔ микросервисы ↔ БД (PostgreSQL/Redis/MongoDB/S3), интеграции | QA + разработчики |
| System | Сквозные сценарии витрины, checkout, back-office | QA |
| Acceptance | Бизнес-сценарии B2C/B2B, UAT | Product Owner + QA |
| Non-functional | Производительность, безопасность, совместимость, доступность | QA + DevOps + Security |

### 6.3. Инструменты
- **API:** Postman/Newman, REST Assured, k6 (нагрузка API)
- **E2E Web:** Playwright / Cypress
- **Mobile:** Flutter integration_test, Appium
- **Нагрузка:** JMeter / k6 / Locust
- **Безопасность:** OWASP ZAP, Burp Suite, сканеры зависимостей (Snyk/Dependabot)
- **Мониторинг тестов:** Prometheus/Grafana, Sentry, ELK
- **CI/CD:** GitLab CI / GitHub Actions (автозапуск smoke/regression)
- **Тест-менеджмент:** Jira + TestRail (или аналог)

Требуется обучение: Playwright, k6, OWASP ZAP (см. раздел 11).

### 6.4. Метрики
- Покрытие требований тест-кейсами (%)
- Покрытие кода unit-тестами (%)
- Defect Density, Defect Leakage
- Pass/Fail rate по уровням
- Время ответа API (p50/p95/p99), пропускная способность
- MTBF (для стабильности), доступность (SLA 99.9%)
- Количество критических/блокирующих дефектов

### 6.5. Конфигурации тестирования
- **Web:** Chrome, Safari, Firefox, Edge (последние 2 версии); desktop + mobile web
- **Mobile:** iOS (2 последние мажорные), Android (2 последние мажорные), планшеты
- **Окружения:** Dev, Staging (интеграционное), Pre-prod, Prod (smoke)
- **Интеграции:** sandbox-среды платёжных/логистических провайдеров, тестовый контур 1С/МойСклад, тестовый Bitrix24/amoCRM

### 6.6. Регрессионное тестирование
- Полная регрессия перед каждым релизом; smoke — на каждый merge в main.
- Автоматизированная регрессия критического пути (P1) — обязательна.
- Регрессия по severity: блокирующие/критические дефекты → расширенная регрессия затронутых модулей.
- Untestable/противоречивые требования эскалируются Product Owner и фиксируются в backlog.

### 6.7. Ограничения
- Зависимость от доступности sandbox-сред провайдеров
- Ограниченные ресурсы тестовых устройств
- Жёсткие сроки релиза (см. раздел 12)

## 7. Item Pass/Fail Criteria

### 7.1. Критерии прохождения (Release-ready)
- **100%** критических (P1) тест-кейсов выполнено, **≥ 98%** успешно
- **0** открытых блокирующих/критических дефектов
- Открытых дефектов уровня Major — не более согласованного порога (например, ≤ 5), с подтверждённым workaround
- Покрытие критических требований тест-кейсами — **100%**
- Все smoke/regression наборы пройдены
- API p95 < 200 мс при целевой нагрузке (10 000 concurrent users на пике)
- Успешный аудит безопасности (нет критических/высоких уязвимостей)
- Подтверждено соответствие PCI DSS (для карт), 152-ФЗ/GDPR
- UAT подписан Product Owner

### 7.2. Критерии провала
- Наличие хотя бы одного открытого блокирующего дефекта на критическом пути
- Невыполнение НФТ по производительности/доступности
- Выявленные критические уязвимости безопасности
- Непройденные ключевые интеграции (оплата/доставка/ERP)

**Различие:** *дефект* — потенциальная причина сбоя (может быть допустим); *сбой (failure)* — наблюдаемое пользователем нарушение работы (недопустим на критическом пути).

## 8. Suspension Criteria and Resumption Requirements

### 8.1. Критерии приостановки
- Среда staging недоступна или нестабильна > 2 часов
- Обнаружен блокирующий дефект, делающий дальнейшее тестирование бессмысленным (например, невозможность checkout)
- Недоступность sandbox платёжного/логистического провайдера
- Количество дефектов превышает порог, при котором новые тесты не дают ценности
- Критический сбой инфраструктуры (K8s, БД)

### 8.2. Возобновление
- Устранение блокирующего дефекта + подтверждение fix'а
- Восстановление среды/провайдера
- Проведение регрессии затронутых областей до возобновления полного цикла
- Пересмотр объёма/сроков при необходимости (см. раздел 12)

> ⚠️ Тестирование после фатальной ошибки без её устранения порождает «фантомные» дефекты — недопустимо.

## Approach

**Общая стратегия:** многоуровневое тестирование — модульное (unit), интеграционное, системное, приёмочное (UAT), плюс специализированные виды: нагрузочное, тестирование безопасности, тестирование совместимости (Web/мобильные/Smart TV/голосовые ассистенты — по мере реализации), регрессионное, тестирование DRM и локализации (допущение: языки — TBD).

**Уровни и распределение:**
- Unit — на стороне разработки (покрытие — TBD, допущение: согласуется в Project Plan).

- Системное — сквозные сценарии (CJM): поиск → карточка → корзина → checkout → оплата → доставка → личный кабинет → библиотека.
- UAT — с участием представителей B2C/B2B и внутренних пользователей (контент-менеджеры, операторы, сотрудники склада).
- Нефункциональное — нагрузка/производительность (API < 200 мс, 10 000 одновременных пользователей), безопасность (PCI DSS, 152-ФЗ/GDPR, DDoS, SQL-инъекции), доступность (SLA 99.9%), отказоустойчивость и auto-scaling в K8s.

**Регрессионные правила:** регрессия запускается при каждом значимом изменении сборки и перед релизом; объём — по severity обнаруженных дефектов и затронутым модулям (детализация — TBD).

## Approach

**Общая стратегия:** комбинированное тестирование — функциональное, интеграционное, регрессионное, нагрузочное, тестирование безопасности и приемочное. Тестирование проводится итеративно в соответствии с Agile/Scrum. Для MVP и Full-версии используются отдельные циклы с последующей регрессией.

- **Уровни тестирования:**  
  - Модульное (разработчики) — вне зоны ответственности QA, но результаты учитываются.  
  - Интеграционное (QA + разработчики) — проверка взаимодействия микросервисов, API, внешних систем.  
  - Системное (QA) — сквозные сценарии на веб-витрине и в админ-панели.  
  - Приемочное (QA + заказчик) — проверка бизнес-требований.  
  - Нагрузочное и стресс-тестирование (QA + DevOps) — проверка производительности и масштабируемости.  
  - Тестирование безопасности (QA + внешний аудитор) — сканирование уязвимостей, проверка соответствия PCI DSS, 152-ФЗ.

- **Инструменты:**  
  - Функциональное тестирование: Playwright (веб), Postman (API).  
  - Нагрузочное: JMeter, Locust.  
  - Безопасность: OWASP ZAP, Burp Suite.  
  - Управление тестами: TestRail (допущение).  
  - CI/CD: GitLab CI (интеграция автотестов).  
  - Мониторинг: Prometheus, Grafana, Sentry.

- **Метрики:** процент пройденных тест-кейсов, количество дефектов по severity, покрытие требований, среднее время отклика API, процент успешных транзакций.

- **Управление конфигурациями:** тестирование проводится на staging-окружении, идентичном production по конфигурации (кроме масштаба). Версии сборок фиксируются в трекере.

- **Регрессионное тестирование:** проводится после каждого значимого изменения; объем регрессии зависит от severity исправленных дефектов. Автоматизированные регрессионные наборы запускаются в CI.

- **Обработка неясных или непроверяемых требований:** такие требования фиксируются в виде вопросов к бизнес-аналитику; до получения ответа тест-кейсы не создаются.

## Item Pass/Fail Criteria

**Критерии прохождения для функционального тестирования (MVP и Full):**
- Все тест-кейсы с приоритетом High выполнены.
- Не менее 95% тест-кейсов пройдено успешно (допущение).
- Дефекты уровня Critical и High отсутствуют или имеют согласованный план исправления с переносом на следующий релиз (для Full).
- Все интеграционные сценарии с внешними системами (платежи, доставка, ERP) выполнены успешно.

**Критерии прохождения для нагрузочного тестирования:**
- Время ответа API < 200 мс для 95% запросов при нагрузке 10 000 одновременных пользователей.
- Отсутствие ошибок 5xx при пиковой нагрузке.
- Автомасштабирование подтверждено: при увеличении нагрузки в 2 раза ресурсы добавляются без деградации.

**Критерии прохождения для тестирования безопасности:**
- Отсутствие уязвимостей уровня Critical и High по результатам сканирования.
- Соответствие требованиям PCI DSS (для платежного модуля) и 152-ФЗ (для персональных данных).

**Критерии прохождения для приемочного тестирования:**
- Все бизнес-сценарии, согласованные с заказчиком, выполнены без блокирующих дефектов.
- Подписан акт приемки.

## Suspension Criteria and Resumption Requirements

**Критерии приостановки тестирования:**
- Обнаружено более 5 дефектов уровня Critical в течение одного тестового цикла.
- Более 20% тест-кейсов блокированы из-за недоступности тестового окружения или критических ошибок сборки.
- Внешняя интеграция (платежный шлюз, логистика) недоступна более 4 часов.
- Нагрузочное тестирование показывает деградацию производительности более чем на 50% от целевых показателей.

**Требования к возобновлению:**
- Устранены критические дефекты, блокирующие тестирование.
- Предоставлена стабильная сборка с исправлениями.
- Восстановлена работоспособность внешних систем.
- Проведена повторная верификация исправлений (smoke-тесты) и регрессия затронутых областей.

## 6. Approach

- **Уровни:** компонентный (в CI разработки), интеграционный, системный, приёмочный, нагрузочный, security.
- **Техники:** эквивалентные классы, граничные значения, таблицы решений, state transition для заказов/подписок/модерации, pairwise для конфигураций, risk-based, exploratory, негативное тестирование, проверка данных и расчётов.
- **Внешние интеграции:** платежи — sandbox ЮKassa/CloudPayments/Stripe; логистика — sandbox/mock Shiptor/GotoRoute и API служб доставки; 1С/МойСклад — тестовый контур; CRM — sandbox; коммуникации — тестовые ключи SendGrid/Twilio/SMS.ru/Telegram; контент-провайдеры и DRM — mock/тестовые DRM-файлы.
- **Регрессия:** после исправления S1/S2 — полная регрессия критичных H-функций; после S3 — целевая регрессия; перед релизом — полный регрессионный набор MVP/Full. Правила severity — по внутренней шкале (допущение).
- **Метрики:** процент выполненных кейсов, pass rate, количество/severity дефектов, покрытие H-функций, p95 времени ответа API, ошибки под нагрузкой, результаты security-сканов.
- **Конфигурации:** Web Chrome/Firefox/Safari/Edge (допущение), Mobile iOS/Android (допущение), AR-устройство/эмулятор (допущение), Smart TV/voice mock (допущение).
- **Нетестируемые/неясные требования:** фиксируются в traceability matrix, уточняются с Product Owner/Tech Lead; не исключаются молча.
- **Ограничения:** доступность sandbox, DRM-контента, платёжных тестовых карт, нагрузочного стенда.

## 7. Item Pass/Fail Criteria

Элемент считается **Pass**, если:
- выполнено не менее 95% запланированных тест-кейсов (допущение);
- все H-функции покрыты тестами на 100% (допущение);
- нет открытых дефектов S1/S2;
- открытых S3 — не более 5 (допущение), каждый с workaround и согласованием;
- API p95 < 200 мс (допущение: метрика p95; порог 200 мс из `task.md`);
- нагрузка 10 000 одновременных пользователей выдерживается с error rate ≤ 1% (допущение; 10 000 из `task.md`);
- security-аудит не выявляет critical/high уязвимостей (допущение);
- SLA 99.9% подтверждается мониторингом/расчётом (99.9% из `task.md`).

Иначе — **Fail**. Для Master Test Plan дополнительно: завершены все запланированные уровни тестирования, отчёты и incident reports актуализированы.

## 8. Suspension Criteria and Resumption Requirements

Тестирование приостанавливается, если:
- обнаружено ≥ 3 дефектов S1 или ≥ 10 дефектов S2 за 24 часа (допущение);
- более 30% тест-кейсов заблокированы из-за неработоспособности сборки (допущение);
- недоступен критичный sandbox/стенд более 4 часов (допущение);
- выявлена потеря/порча тестовых данных или риск для реальных данных;
- security-инцидент critical.

Возобновление: после исправления блокирующих дефектов, smoke-теста, проверки среды и целевой/полной регрессии по правилам раздела 6. Влияние на сроки фиксируется в Schedule и Risks.

## 14. Schedule

В `task.md` длительности заданы диапазонами: Discovery 1–2 мес., MVP 3–4 мес., Full 3–4 мес.; Design 2 мес. и QA 1 мес. — фиксированные. Принято 1 месяц = 4 недели **(допущение)**. MVP testing 4 недели и Full testing 6 недель — **(допущение)**. Soft Launch 2 недели — **(допущение)**. Старт = неделя 0.

**Базовый сценарий:** Full-разработка **не идёт параллельно** с тестированием MVP: она стартует после завершения MVP testing, чтобы не смешивать фиксы MVP и Full.

| Этап | Нижняя граница, длит. | Нижняя граница, недели | Верхняя граница, длит. | Верхняя граница, недели |
|---|---:|---:|---:|---:|
| Discovery & Аналитика | 4 | 0–4 | 8 | 0–8 |
| Проектирование и Дизайн | 8 | 4–12 | 8 | 8–16 |
| Разработка MVP | 12 | 12–24 | 16 | 16–32 |
| Тестирование MVP | 4 (допущение) | 24–28 | 4 (допущение) | 32–36 |
| Разработка Full | 12 | 28–40 | 16 | 36–52 |
| Тестирование Full | 6 (допущение) | 40–46 | 6 (допущение) | 52–58 |
| QA и нагрузочное тестирование | 4 | 46–50 | 4 | 58–62 |
| Релиз/Soft Launch | 2 (допущение) | 50–52 | 2 (допущение) | 62–64 |
| **Итого** |  | **52 недели** |  | **64 недели** |

Проверка суммы: нижняя 4+8+12+4+12+6+4+2 = **52**; верхняя 8+8+16+4+16+6+4+2 = **64**. MVP testing начинается после поставки MVP-сборки: нед. 24/32. Full testing — после Full-сборки: нед. 40/52.

Если бизнес потребует параллельного старта Full-разработки после поставки MVP-сборки, календарный срок сокращается на 4 недели: lower 48, upper 60, но возрастает риск конфликтов сборок и регрессии. Это не базовый сценарий.
